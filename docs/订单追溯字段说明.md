# 销售订单 / 采购订单追溯字段说明（ERP-008）

> 任务：`ERP-008` 完整化销售订单与采购订单追溯（外销合同 + 来源单据 + 采购执行）。
> 范围：`src/ERP.Domain`、`src/ERP.Application`、`src/ERP.Infrastructure`、`src/ERP.Api`、`src/ERP.UnitTests`、`src/ERP.IntegrationTests`。
> 不改动任何 SQL 脚本、`deploy/**`、`release/**`、`checkpoints/**`、`SeedData*.cs`；生产库、生产 OSS、正式部署与不可逆数据操作仍由 Human Gate 控制。

## 1. 背景与结论

ERP-006 审计把「销售订单（外销合同）」「采购订单」判为 **partial**：字段与页面都缺少外贸合同、来源追溯与采购执行所需的列，且采购单无法归属客户 / 销售订单（代理出口无法核算单客户毛利）。

ERP-008 的落地口径：

1. **销售订单与采购订单统一由 EF 主子表承载**（`db_owner.SalesOrders` / `db_owner.PurchaseOrders`，与报表 `ReportService` 读取的表一致），不再从菜单进入存储过程版单据页（`sp_Biz_SalesOrder` / `sp_Biz_PurchaseOrder` 的 `BILL_CONFIG` 页仍保留定义，供历史数据排查与回滚参考）——这样新增列不需要 `DROP/CREATE` 生产存储过程。
2. **新列一律带安全默认值**（空串 / 0 / 0 位），历史单据可正常打开、列表与打印不受影响。
3. **结构升级幂等**：`SchemaUpgrader.EnsureUpgradedAsync` 第 22 段以 `OBJECT_ID + COL_LENGTH` 双保险补齐缺列，表不存在时不会中断服务启动。

## 4. 页面与打印 / 导出

- 「订单管理 → 销售订单」「订单管理 → 采购订单」由 `modules-doc.js` 的模块配置驱动 `crud.js` 主子表页面：客户 / 供应商 / 业务员为**引用字段**（可搜索选择），币种 / 价格条款 / 出口方式 / 业务性质 / 是否含税 / 到货与结算进度为**下拉选择**，多行文本字段（Consignee / Notify / 唛头 / 验货 / 包装要求）为 textarea；明细行「数量 × 单价 = 金额」自动计算并汇总。
- 行操作「打印预览」经 `sales-pi.js` 的 `SALES_DOC_PRINT` 配置渲染单据，新增字段与唛头 / 验货 / 包装要求区块一并输出；打印模板类型沿用 `sales-order` / `purchase-order`（打印设计页可用）。
- 「订单管理 → 销售订单导出 / 采购订单导出」菜单改调 EF 的 `export-excel`，状态筛选口径为订单状态（待提交 / 已提交 / 已审核 / 已取消），导出列包含全部新增字段。
- **来源单据带入（ERP-010）**：报价单 / PI 列表的「更多」菜单提供两个动作——「带入预填销售订单」（按来源单据打开销售订单新增表单，字段与明细已带入，可继续编辑，保存走 `/api/sales-orders`）与「转销售订单」（服务端一次生成，来源自动留痕）。带入后 `来源报价单 ID / 号`、`来源 PI ID / 号` 字段会随表单提交写入，重新打开该订单即可看到追溯链。
- **比价选中行带入采购订单（ERP-020）**：「供应商与采购 → 供应商比价」列表中**状态为「已选中」**的行会在「更多」菜单显示「生成采购订单」与「预填采购订单」两个动作（未选中 / 已放弃行不显示，服务端仍二次校验）。「预填」切到采购订单页并打开已带入的新增表单（不落库、不占用单据号），保存走 `/api/purchase-orders`；「生成」由服务端一次落库，并在比价行留下来源痕迹：状态置 `已转采购订单`、`RefOrderNo` 写回生成的采购单号，采购订单备注追加 `来源比价 <比价批次号>（比价行 #<Id>）`。

- **比价批次转采购订单（ERP-027）**：同一比价页提供两个批次入口——行操作「批次转采购订单」（仅在状态为「已选中」的行显示，按其所属批次号触发）与工具栏「📦 批次转采购订单」（直接输入批次号）。点击后**先取只读计划**（`batch-order-plan`）并弹出确认框，说明「将把多少行合并为多少张采购订单、每张的供应商 / 币种 / 行数与重算合计、以及多少行不合格会被跳过」；确认后才调用 `batch-to-order` 一次落库，成功提示条给出生成的采购单号清单。

### 4.2 采购执行进度派生（ERP-026）

采购订单列表行操作新增「执行进度」（`modules-doc.js` → `purchase-order-progress.js`），调用 `GET /api/purchase-orders/{id}/progress`（`PurchaseOrderProgress.ForPurchaseOrderAsync`）。该接口**只读派生**：不落库、不改单据状态、不新增或修改任何表列；界面把「派生值」与「人工登记值」并列展示，二者互不覆盖。同一页面的「执行时间线」由 ERP-022 提供（`GET /api/purchase-orders/{id}/timeline`）。

**收货数量（`StockIn` + `StockInDetail`，来源引用 `StockIn.PurchaseOrderId`）**

| 输出 | 口径 |
|---|---|
| `orderedQuantity` | 采购订单未删除明细的数量合计 |
| `receivedQuantity` | 以本单为来源、未删除、**状态 = 已审核**的入库明细数量合计（ERP-023 起入库明细已折算基础单位，与订单明细同口径比较） |
| `pendingQuantity` | 同口径但状态为**待提交 / 已提交**（未审核，单列、不计入已收） |
| `outstandingQuantity` | Σ 订单行未收数量 = Σ max(0, 订单数量 − 已冲抵已收数量) |
| `matchedReceivedQuantity` / `unmatchedReceivedQuantity` | 已冲抵订单明细的已收数量（含超收）/ 订单外商品（订单明细中不存在该商品）的已收数量；两者之和 = `receivedQuantity` |
| 行 `overReceivedQuantity` | 订单行超收部分；同一商品多行时由该商品的**最后一行**吸收剩余数量 |
| `receiptStatus` | `none` / `partial` / `complete` / `over_received`（整体与逐行同一词表） |

- **不计入已收**：已驳回 / 已取消入库单、软删除入库单、以其它采购订单为来源的入库单；采购退货与库存调整单不冲减已收数量（另行核算）。
- `arrivalProgressConsistent`：把人工登记的到货进度（未到货 / 部分到货 / 已到货）与派生状态比对；文本为空或不在词表内时为 `null`（无法判定），不猜测、不改写字段。
- 结果同时列出收货来源入库单引用（单号 / 日期 / 状态 / 数量 / 是否计入），便于逐单核对。

**结算金额（只在既有引用可用时暴露）**

- 既有结构中**不存在**「采购订单 ↔ 付款单」的直接引用：`FinancePayment` 只记录供应商（另有可空 `PaymentApplyId`），`FinancePaymentApply` 只引用销售订单。因此只有下面这条链完整且唯一时才算「引用可用」：
  `FinancePayment.SupplierId = 本单供应商` 且 `FinancePayment.PaymentApplyId → FinancePaymentApply.SalesOrderId = 本单归属销售订单 Id`，且该归属销售订单下**只有本单一张未删除采购订单**。
- `linkStatus = linked` 时才给出金额：`settledAmount`（已审核且**币种与本单一致**的付款单合计）、`outstandingAmount`（= 订单总额 − 已结算，最小 0）、`submittedAmount`（已提交 / 待提交，同口径）；`overSettled` 标记超付。引用成立但找不到货款申请单时，已结算按 0、未结算按订单总额返回（引用成立，不是猜测）。
- `linkStatus = ambiguous`：归属销售订单下存在多张采购订单，付款单无法唯一归属到本单 → 金额一律 `null`。
- `linkStatus = unavailable`：本单未关联归属销售订单，或未维护供应商 → 金额一律 `null`，`linkReason` 说明缺什么。
- 币种不一致的付款单只列出（`counted = false`）且**不做汇率换算**；供应商不符、未引用货款申请单的付款单不列入；**按供应商汇总、或按备注 / 事由文本匹配都不作为本单结算依据**。`null` 表示未知，界面显示「未知」，绝不显示为 0。
- `recordedProgress` 原样回显订单已落库的结算进度文本（人工维护的字段），派生结果不写回该字段。

**查询有界**：固定 1 次订单（含明细）+ 1 次入库主表 + 1 次入库明细 + 1 次归属销售订单下采购订单计数 + 1 次货款申请单 + 1 次付款单，各集合按 200 条上限截断，无 N+1，与订单 / 单据数量无关。

### 4.3 比价批次 → 采购订单（ERP-027）

同一比价批次（相同 `PurchaseQuote.QuoteNo`，即「同一需求多家报价」）内的**已选中**行可以一次性转成采购订单：兼容的行合并为同一张订单，不兼容的行独立成单，不合格的行明确跳过。

**资格与跳过（逐行复用单行权威守卫，不复制规则）**

| 情形 | 处理 |
|---|---|
| `IsSelected = true` 且状态为 `已选中`、已维护供应商、数量 > 0、单价 ≥ 0，且未生成过采购订单 | 参与本次转换（与 ERP-020 单行转换同一套 `BuildDraftAsync` 守卫与映射） |
| 状态 `已转采购订单`，或 `RefOrderNo` 指到既有采购订单 / 采购订单备注含该行来源标记 | 跳过，原因「已生成采购订单：{单号}，不能重复生成」 |
| 已放弃 / 未选中供应商 / 未维护供应商 / 数量 ≤ 0 / 单价 < 0 | 跳过，原因与单行守卫文案完全一致 |
| 批次内**没有任何**合格行 | `batch-to-order` 抛 `RuleConflict`（消息含跳过原因的分组计数），**不落库、不占单据号**；只读计划接口返回 0 组 + 跳过清单 |
| `lineIds` 给定的行不属于该批次 | 抛 `InvalidParameter`（不转换任何行） |

**合并分组（`BatchGroupKey`：供应商 + 币种 + 归属客户 + 归属销售订单 + 付款条件 + 是否含税）**

- 组内这些**采购订单表头字段完全一致**时才能合并：两张来源行的供应商 / 币种（枚举解析后）/ 归属客户 / 归属销售订单（`RefOrderNo` 解析结果）/ 付款条件（去空格、不区分大小写）/ 是否含税只要有一项不同，就各自独立成单——绝不静默改写来源值，也不做「多数表决」「按第一行覆盖」这类猜测。
- 组内金额与数量差异全部落在**明细行**上：每行来源行对应一行明细（商品 / 规格 / 单位 / 数量 / 单价 / 金额），服务端按 `数量 × 单价` 重算每行金额，订单总额按 `PurchaseOrderController.Calculate` 重算（不采信比价行的报价总额）。
- 交期：明细保留各自交期（`今天 + DeliveryDays`，`≤ 0` 留空），**订单交期取组内最晚一行**（一单承诺覆盖所有行），供应商确认交期同口径；组内全部为零交期时订单交期留空。
- 复用 `MapDraft` 的全部映射口径（汇率 1、税率 0、采购员 / 代垫 / 执行进度保持默认、归属客户与归属销售订单解析等，见 §4.1）。

**来源留痕（不改任何数据库结构）**

- 每张生成的采购订单备注 = 来源行的父备注（去重）+ 每行来源标记 `来源比价 <批次号>（比价行 #<Id>）`；父备注过长时**先截断父备注、保留来源标记**（标记是重复生成的第二道判据），整列截断到 500 字符。
- 每行明细备注同样写入该行的来源标记，行级可追溯（哪一行报价 → 哪一行明细）。
- 每条已转换的比价行：状态置 `已转采购订单`、`RefOrderNo` 写回**其所属订单**的采购单号；未转换（不合格）行不改状态、不改 `RefOrderNo`。

**重复保护与单号**

- 重复转换由既有两道守卫拦截（`RefOrderNo` 链接 + 备注来源标记）；第二次调用同一批次会抛 `RuleConflict` 且不新增订单、不新增明细、不覆盖 `RefOrderNo`。批次路径与单行路径共用同一守卫，因此「先批次转、再单行转」或反之都不会重复生成。
- 生成的采购订单被软删除且来源行回退（状态改回 `已选中`、清空 `RefOrderNo`）后允许重新生成（与 ERP-010 / ERP-020 同一口径）。
- 单据号：先向 `IDocumentNumberService` 取候选号，再经 `EnsureUniqueOrderNoAsync` 保证**批次内互不相同**（与库内既有单号或本批次已分配号冲突时按 ERP-019 单证编号的既有约定追加 `-2 / -3 …`）；全部取号发生在任何单据落库之前，批次内不会出现「号一样的两张单」或半成品数据（批次整体一次 `SaveChanges` 提交）。

**只读计划（`GET batch-order-plan`）**

- 返回：`sourceNo`、批次行数 `batchLineCount`、可转换行数 `eligibleLineCount`、将生成的张数 `groupCount`、重算合计 `totalAmount`、每组明细（`supplierId/Name`、`currency`、`owningCustomer*`、`owningSalesOrderNo`、`paymentTerms`、`taxIncluded`、`deliveryDate`、`lineIds`、`lineCount`、`totalAmount` 与**未落库草稿** `order`）以及跳过清单 `skipped[{ lineId, quoteNo, productName, reason }]`。
- 只读：不写库、不占单据号、不改来源状态、不刷新审计时间（前端据此展示确认文案，用户可取消）。

**查询有界**：批次内固定 **2 次**预取查询（该批次 `RefOrderNo` 指向的销售订单；该批次既有来源采购订单，按采购单号回写与备注标记前缀一次查回后内存匹配）+ 批次行 1 次 + 落库前 1 次取回要留痕的来源行，无按行 N+1。

### 4.4 供应商采购敞口报表（ERP-031）

采购订单页工具栏新增「供应商采购敞口」入口（`modules-doc.js` → `supplier-purchase-exposure.js`），调用 `GET /api/purchase-orders/supplier-exposure`（`SupplierPurchaseExposure.ForQueryAsync`）。该报表**只读派生**：不落库、不改单据状态、不新增或修改任何表列，也不创建发票 / 应付记录。

> **与应付账款台账 / 账龄表的边界（重要）**：本报表是采购订单的**运营敞口视图**，不是 AP 台账、不是账龄表 —— 不基于发票、不推算账期与到期日、不做账龄分摊，也不按供应商汇总口径或备注文本猜测单据链接；`unlinkedOrderedAmount`（未链接敞口）只是尚未按既有引用归属到订单的订单金额，**不得当作应付余额或据以付款**。

**分组与金额（不同币种绝不合并）**

| 输出 | 口径 |
|---|---|
| 分组键 | `supplierId` + `currency`：只有同一供应商 + 同一币种才汇总金额；不同币种分别成行，**不做汇率换算、不存在跨币种总额** |
| `orderedAmount` | 采购订单已落库总额（`PurchaseOrder.TotalAmount`，即 §4.1 的「Σ 明细数量 × 单价」），报表不重算 |
| `linkStatus` | `linked` / `ambiguous` / `unavailable`，与 §4.2 的结算引用链**同一套规则**（付款单 → 货款申请单 → 本单归属销售订单，且该销售订单下只有本单一张采购订单），不引入第二套匹配算法 |
| `settledAmount` / `outstandingAmount` / `submittedAmount` | 复用 ERP-026 口径：仅 `linked` 订单给出（已审核且币种一致的付款单计入已结算；未结算 = 订单金额 − 已结算，下限 0）；`ambiguous` / `unavailable` 一律 `null`（未知，不等于 0） |
| `linkedOrderedAmount` | 链接可用订单的订单金额合计 |
| `unlinkedOrderedAmount` | 链接不唯一 / 无可用引用订单的订单金额合计，**显式单列**，不并入任何权威已结算 / 未结算合计 |
| `currencies[]` | 本页按币种汇总（币种 / 供应商数 / 订单数 / 订单金额 / 三种链接状态计数 / 已结算 / 未结算 / 未链接敞口）：同币种跨供应商汇总、不同币种分行展示 |

**收货（只作数量口径，不用来推算金额）**

- 每张订单另附 `orderedQuantity` / `receivedQuantity` / `outstandingQuantity` / `pendingQuantity` / `receiptStatus`，全部复用 §4.2 的已审核入库派生（入库明细已折算基础单位；待提交 / 已提交单列，已驳回 / 已取消 / 软删除不计）。
- 金额一律**不**由「收货数量 × 单价」推算（入库明细没有成本列），因此收货数量只用数量核对，不参与任何金额合计。

**筛选与分页**

- 筛选：`supplierId`、`currency`（枚举名，大小写不敏感）、`orderDateFrom` / `orderDateTo`（含首尾当天）、`linkStatus`、`keyword`（采购单号 / 采购合同号 / 归属销售订单号）。
- `linkStatus` 是派生值：报表用**与派生规则等价的既有列条件**在数据库侧筛选（未关联归属销售订单或未维护供应商 = `unavailable`；归属销售订单下另有一张未删除采购订单 = `ambiguous`；其余 = `linked`），避免为了筛选而做无界内存过滤；单元测试断言「筛选结果 ≡ 派生结果」，防止两处口径分叉。
- 分页：默认 50、上限 200；排序 = 供应商 + 币种 + 订单日期 + 单据 Id（稳定，翻页不重不漏）；`total` 为筛选后的采购订单总数；`currencies` / `groups` 的合计与计数**只统计本页**（`scopeNote` 同源说明）。

**查询有界（固定次数，无 N+1）**：1 次计数 + 1 次分页 Id + 1 次本页订单（含明细）+ 1 次供应商名 + 收货 2 次（入库主表 / 入库明细）+ 结算 3 次（归属销售订单下采购订单计数 / 货款申请单 / 付款单），与页大小、订单 / 单据数量无关；全程不写库。
**批量上限的诚实处理**：收货与结算的批量查询各有单次上限 2,000 行；命中上限时无法把「被截断的行」归因到具体订单，因此**不静默给出不完整数字** —— 收货数量记 `null`（`receiptStatus = unknown`）、结算金额记未知（`linkStatus = ambiguous`，`linkReason` 说明「达到单次查询上限」），并提示收窄筛选或减小每页条数。单张订单的执行进度（§4.2）仍沿用 200 行上限的既有语义。

### 4.5 销售订单出货 / 财务进度报表（ERP-032）

销售订单页新增两个入口（`modules-doc.js` → `sales-order-progress.js`）：行操作「出货进度」（逐单 `GET /api/sales-orders/{id}/progress`）与工具栏「🚚 出货 / 财务进度」（报表页 `GET /api/sales-orders/shipment-finance-report`）。两者都**只读派生**：不落库、不改单据状态、不新增或修改任何表列，也不创建发票 / 应收记录。

> **与应收账款台账 / 账龄表的边界（重要）**：本报表是销售订单的**出货 / 收款链接视图**，不是应收账款台账、不是账龄表 —— 不基于发票、不推算账期与到期日、不做账龄分摊，也不按客户汇总口径或备注文本猜测单据链接；`uncoveredAmount`（未覆盖金额）只是订单金额与权威计入金额之差，**不得当作应收余额或据以催收**。

**出货数量（数量口径，不用来推算金额）**

| 输出 | 口径 |
|---|---|
| 来源 | 只取 `StockOut.SalesOrderId` 指向本单且未删除的销售出库单；出库明细已折算基础单位（ERP-023） |
| `shippedQuantity` | 只有**已审核**出库单的明细计入；待提交 / 已提交单独计为 `pendingShipmentQuantity`；已驳回 / 已取消 / 软删除一律不计 |
| 冲抵规则 | 同商品多行按明细顺序依次冲抵（该商品最后一行吸收剩余数量，超发体现在订单行上 `overShippedQuantity`） |
| 订单外商品 | 出库明细商品不在本订单明细中时显式单列（`unmatchedShippedQuantity`），不并入订单行 |
| 出货状态 | `none` / `partial` / `complete` / `over_shipped`；命中单次派生上限时为 `unknown`（数量记 `null`） |
| 不叠加流水 | ERP-025 的库存流水是同一批出库凭证的账簿记录（按基础单位），报表**不再叠加**，避免重复计数 |
| 不冲减 | 销售退货与库存调整**不冲减**已出货数量（退货凭据可能只覆盖部分渠道，避免低估出货） |

**收款链接（复用 ERP-028 的既有引用规则，不引入第二套匹配算法）**

| 输出 | 口径 |
|---|---|
| 权威引用 | 只有定金申请单 / 货款申请单以 `SalesOrderId` 指向本单时才是权威引用 |
| `linkedAmount` | 「权威引用 + 已审核 + 币种与本单一致」的记录金额合计；他币种与未审核（待提交 / 已提交）记录**仅列出、不计入、不做汇率换算** |
| `uncoveredAmount` | 订单金额 − 已关联金额；负数表示超收（`overReceived`）；它**不等于**未收款金额 |
| 链接状态 | `linked`（权威引用全部可计入）/ `partial`（部分可归属：存在他币种 / 未审核 / 非已审核记录）/ `unlinked`（没有任何指向本单的收款申请）/ `unknown`（命中派生上限） |
| 未链接的取值 | `unlinked` 时已关联 / 未覆盖金额记 `null`（未知），**不用 0 顶替**：本单没有收款申请 ≠ 客户没有付过款 |
| 客户级记录 | 收款单 / 装柜结算单 / 散货结算单只记录客户、没有订单级引用 → 一律作 `unattributedRecordCount` 单列，不计入、不汇总（多币种不换算） |
| 与 ERP-028 的差异 | 引用字段与计入规则完全一致（测试断言 linked / partial 两档的 `linkedAmount` / `submittedAmount` 与 `OrderFinanceReconciliation` 相等）；仅状态分档层次不同，且 ERP-028 对「引用完整但空集」按 0 呈现、本报表按验收口径记未知 |

**筛选与分页**

- 筛选：`customerId`、`currency`（枚举名，大小写不敏感）、`orderDateFrom` / `orderDateTo`（含首尾当天）、`shipmentStatus`、`financeLinkStatus`、`keyword`（订单号 / 外销合同号 / 客户 PO 号）。
- `shipmentStatus` 只提供可用既有列条件**精确表达**的两档：`none`（不存在「以本单为来源、未删除、已审核」的出库单）/ `shipped`（存在）。「部分 / 齐 / 超」需要按商品逐行冲抵数量，无法用稳定的既有列条件在数据库侧等价表达，因此不做成筛选项、只在行内以派生状态呈现 —— 避免「筛选口径 ≠ 派生口径」两套算法分叉。
- `financeLinkStatus` 提供 `linked` / `partial` / `unlinked` 三档，用与派生规则等价的既有列条件在数据库侧筛选（是否存在指向本单的定金 / 货款申请单、是否全部「已审核 + 同币种」）；`unknown` 只在命中等派生命中上限时出现、无法用既有列条件等价表达，故不提供该筛选项。
- 分页：默认 50、上限 200；排序 = 客户 + 币种 + 订单日期 + 单据 Id（稳定，翻页不重不漏）；`total` 为筛选后的未删除销售订单总数；`groups` / `currencies` 的合计与计数**只统计本页**（`scopeNote` 同源说明）。

**查询有界（固定次数，无 N+1）**：1 次订单集合（筛选 / 计数 / 分页共用）+ 1 次本页订单 + 1 次客户名 + 派生 8 次（订单明细 / 出库主表 / 出库明细 / 定金申请单 / 货款申请单 / 收款单 / 装柜结算单 / 散货结算单），与页大小、订单 / 单据数量无关；全程不写库。
**批量上限的诚实处理**：单张订单每类来源上限 200 行、一页多张订单上限 2,000 行；命中上限时无法把「被截断的行」归因到具体订单，因此**不静默给出不完整数字** —— 出货数量记 `null`（`shipmentStatus = unknown`）、收款金额记未知（`financeLinkStatus = unknown`，`linkReason` / `note` 说明「超过单次派生上限」）。

### 4.6 客户订单与收款核对报表（ERP-046）

销售订单页新增一个工具栏入口（`modules-doc.js` → `sales-order-receipt-reconciliation.js`）：「🧾 订单 / 收款核对」（报表页 `GET /api/sales-orders/receipt-reconciliation-report`）。报表**只读派生**：不落库、不改单据状态、不新增或修改任何表列，也不创建发票 / 应收记录。

> **与应收账款台账 / 客户对账单 / 收款授权 / 账龄表的边界（重要）**：本报表是订单与**收款证据**的核对视图，不是应收账款台账、不是具有法律效力的客户对账单、不是收款授权或结算结果，也不是账龄表 —— 不推算账期与到期日、不做账龄分摊、不判断是否已收讫；`uncoveredAmount`（未覆盖金额）只是订单金额与权威计入金额之差，**不得当作应收余额或据以催收**。

**订单侧（数量与金额完全复用 ERP-032 的同一套派生，不引入第二套匹配算法）**

| 输出 | 口径 |

| `linkedReceiptAmount` | 只按「定金申请单 / 货款申请单的 `SalesOrderId` 指向本单」这一权威引用派生，且只有「已审核 + 币种与本单一致」计入已关联收款金额；他币种 / 未审核 / 非已审核记录仅列出、不计入、不做汇率换算 |
| `pendingReceiptAmount` | 未审核（待提交 / 已提交）收款申请金额，仅单列、不计入 |
| `uncoveredAmount` | 订单金额 − 已关联收款金额；负数表示超收（`overReceived`）；**不等于**未收款金额，也不是应收余额 |
| `receiptCoverageStatus` | `linked`（权威引用全部可计入）/ `partial`（部分可归属：存在他币种 / 未审核 / 非已审核记录）/ `unlinked`（没有任何指向本单的收款申请）/ `unknown`（命中派生上限） |
| 未知的取值 | 覆盖状态为 `unlinked` / `unknown` 时 `linkedReceiptAmount` 与 `uncoveredAmount` 记 `null`（未知），**不用 0 顶替**：本单没有收款申请 ≠ 客户没有付过款，也不代表未收 / 逾期 / 已结清 |

**收款证据侧（收款单没有订单级引用 → 未关联证据单独列出）**

| 输出 | 口径 |
|---|---|
| 来源 | 收款单 `FinanceReceipt` 只记录客户（`FinanceReceipt.CustomerId`），没有任何订单级引用 → 链接状态恒为 `unlinked` |
| 不匹配 | 系统**绝不**按客户名、订单号文本、日期或金额相似度把收款单归到任何销售订单（即使客户、金额、日期与订单完全相同） |

| `unlinkedReceiptCurrencies` | 未关联收款证据**按收款单自身币种**汇总（不同币种分别成行，绝不合并、绝不换算）；该表与订单侧 `currencies` **相互独立，不得相加** |
| 证据分档 | `active`（已审核，计入有效合计）/ `pending`（待提交 / 已提交，仅列出）/ `historical`（已驳回 / 已取消 / 已完成，仅历史核对）；后两者金额永不并入有效合计 |
| 软删除 | 软删除收款单一律不出现在任何筛选结果中（既有状态列无法表达「已删除」，因此不提供该历史可见性） |
| 收款日期 | 订单日期筛选**不作用于**收款单（收款单没有订单日期），收款单按自身收款日期原样列出 |

**筛选与分页**

- 筛选：`customerId`、`currency`、`orderDateFrom` / `orderDateTo`（含首尾当天）、`shipmentStatus`（`none` / `shipped`）、`receiptLinkStatus`（`linked` / `partial` / `unlinked`）、`receiptStatus`（`active` 默认 / `pending` / `historical` / `all`）、`orderStatus`（`active` 默认排除已取消 / `cancelled` 仅历史 / `all`）、`keyword`（订单号 / 外销合同号 / 客户 PO 号）。
- 状态筛选全部用与派生规则**等价的既有列条件**在数据库侧筛选（是否存在指向本单的收款申请及其状态与币种、是否存在已审核出库单、`SalesOrder.Status`、`FinanceReceipt.Status`），避免为了筛选做无界内存过滤，也避免两处口径分叉；`unknown`（命中派生上限）无法用既有列条件等价表达，故不提供该筛选项。
- 已取消订单默认**不并入有效合计**（`orderStatus = cancelled / all` 提供历史视图并单列 `cancelledOrderCount`，其数量 / 金额仅作历史参考）；软删除订单一律排除。历史 / 未审核收款证据必须显式选择 `receiptStatus` 才可见。
- 分页：默认 50、上限 200；排序 = 客户 + 币种 + 订单日期 + 单据 Id（稳定，翻页不重不漏）；`total` 为筛选后的未删除销售订单总数；`groups` / `currencies` / `unlinkedReceipts` / `unlinkedReceiptCurrencies` 的合计与计数**只统计本页**（`scopeNote` 同源说明）。

**查询有界（固定 12 次，无 N+1）**：订单集合（筛选 / 计数 / 分页共用）+ 本页订单 + 客户名 + 派生 8 次（订单明细 / 出库主表 / 出库明细 / 定金申请单 / 货款申请单 / 收款单 / 装柜结算单 / 散货结算单）+ 未关联收款证据 1 次，与页大小、订单 / 收款单数量无关；全程不写库。
**批量上限的诚实处理**：单张订单每类来源上限 200 行、一页多张订单上限 2,000 行，未关联收款证据单次上限 2,000 行。命中上限时**不静默给出不完整数字** —— 覆盖金额记 `null`（`receiptCoverageStatus = unknown`）、收款证据汇总金额记 `null` 且 `pageUnlinkedReceiptTruncated = true`（界面显式提示「不完整」，请收窄筛选）。

## 5. 校验规则


- 销售订单：`CommissionRatio` 必须在 0~100（越界抛 `InvalidParameter`，事务内不落库）。
- 采购订单：`TaxRate` 必须在 0~100。
- 比价 → 采购订单资格（ERP-020，服务端唯一权威）：`IsSelected = true` 且状态不为 `已放弃` / `已转采购订单`，供应商必须已维护，需求数量必须 > 0、报价单价不得为负；违反时分别抛出 `RuleConflict` / `InvalidParameter`，且**不落库、不改来源单据**。
- 比价 → 采购订单重复守卫（两道，全部只读既有列、不新增结构）：① 比价行 `RefOrderNo` 指向的未删除采购订单（人工把状态改回「已选中」也不会重复生成）；② 采购订单备注中的来源标记（防止人工清空 `RefOrderNo` 后再次生成）。生成过的采购订单被软删除后允许重新生成（与「报价单 / PI 转销售订单」同一口径）。
- 比价批次 → 采购订单（ERP-027）：批次号与比价行 Id 至少给一个（否则 `InvalidParameter`）；批次不存在 / 比价行不存在抛 `NotFound`；`lineIds` 内的行必须属于该批次（否则 `InvalidParameter`）；逐行资格与重复守卫与单行路径同一套（不合格行进入 `skipped` 清单而非静默丢弃）；批次内无任何合格行时 `batch-to-order` 抛 `RuleConflict`，只读计划接口照常返回 0 组 + 跳过原因。分组只按 `BatchGroupKey` 全等，不合并表头不一致的行，也不改写来源值。
- 供应商采购敞口报表（ERP-031）：`currency` 必须是币种枚举名（CNY / USD / EUR / HKD / GBP / JPY），`linkStatus` 必须是 `linked` / `ambiguous` / `unavailable`，订单日期区间不得倒置 —— 违反时抛 `InvalidParameter`（不静默忽略筛选条件）；`supplierId ≤ 0` 视为不筛选，`pageSize` 钳制到 1~200、`page` 最小 1。报表只有 1 个 GET 路由，无任何创建 / 修改 / 核销入口。
- 销售订单出货 / 财务进度报表（ERP-032）：`currency` 必须是币种枚举名，`shipmentStatus` 必须是 `none` / `shipped`，`financeLinkStatus` 必须是 `linked` / `partial` / `unlinked`，订单日期区间不得倒置 —— 违反时抛 `InvalidParameter`（不静默忽略筛选条件）；`customerId ≤ 0` 视为不筛选，`pageSize` 钳制到 1~200、`page` 最小 1。报表与逐单进度各自只有 1 个 GET 路由（无创建 / 修改 / 核销入口），进度接口对不存在的订单抛 `NotFound`；金额 / 数量为 `null` 一律表示未知，不回落为 0。
- 定金比例沿用既有口径（总额 × 比例），明细金额与订单总额、定金由服务端重算。
