# 供应商付款关联采购发票说明（ERP-066）

## 1. 背景与定位

ERP-049 已建立**供应商付款引用登记册**（`SupplierPaymentAllocations`），把「某张付款单指向了哪几张**采购订单**」
变成可登记的引用证据；ERP-043 / ERP-065 又建立了**供应商采购发票登记册**（`PurchaseInvoices` /
`PurchaseInvoiceAllocations`），把普票 / 专票 / 进口发票的证据与可选到期日、付款条件登记下来。
但在实际对账里，用户还需要一项此前**无法显式登记**的事实：**这笔付款到底对应哪几张采购发票**。

本次（ERP-066）新增**供应商付款 → 采购发票 付款引用登记册**（`SupplierPaymentInvoiceAllocations`）：

- 在**既有、未删除**的付款单与**既有、已登记（未作废）**的采购发票之上登记引用（分摊）行：
  一行 = 一张付款单 → 一张采购发票 + 一个引用金额；
- 引用只按**权威一致性**（同供应商 + 同币种、发票已登记未作废）建立，
  **不按号码相似度、金额相近、日期接近猜测发票**；
- 付款单侧展示**已引用 / 未引用金额**，发票侧展示**已引用 / 未引用含税总额**，两侧未引用金额都**不被猜测**；
- 更正走**显式作废**（必填原因）：保留原始金额、快照、登记人与历史，不提供硬删除、改派与静默替换。

定位：**付款引用证据登记册（发票维度）**。它**不是**银行付款凭证、**不是**应付账款核销、
**不是**发票认证 / 抵扣、**不是**税务申报，也**不是**供应商余额。登记 / 作废一行都**不会真的付款、
不会移动资金、不会把发票或采购订单标记为已结清**，也不引入第二套账务引擎
（不记账、不生成凭证 / 收付款 / 结算单）。

**审计结论（唯一主数据与唯一分配模型）**：仓库内既有的供应商付款主数据只有**一份**
（`FinancePayments`，含付款单号 / 日期 / 供应商 / 金额 / 币种 / 方式 / 账户 / 状态），
供应商采购发票登记也只有**一份**（`PurchaseInvoices`，ERP-043 建立、ERP-065 扩展，含可选到期日与付款条件）。
因此本任务**不新建**任何付款单表、付款明细表或第二套发票登记册，也不复制金额到新主体表，
只在两者之上新增**唯一一张**显式分配证据表 `SupplierPaymentInvoiceAllocations`：
付款单与发票都以**持久化 Id** 引用，其余字段全部是写入时的服务端权威快照。

> 本说明对应改动**不含**任何历史数据回填，也**不新增或修改付款单、采购发票与采购订单的任何列**；
> 新增的只有 `SupplierPaymentInvoiceAllocations` 一张表（幂等建表 + 索引，见第 8 节）。

## 2. 字段与快照口径

| 字段 | 口径 |
|---|---|
| 付款单 | 必须**存在且未删除**（付款单状态不限；本册不改变付款单状态，只保存写入时的状态快照） |
| 付款单快照 | 单号 / 付款日期 / 状态 / 状态文案 / **付款金额**（原币，写入时取自付款单，作为有效行金额合计上限） |
| 采购发票 | 必须**存在、未删除且已登记**（`Status = 1`）；**草稿与已作废发票一律拒绝**（历史引用仍可读）；供应商与币种都必须与付款单**一致** |
| 发票快照 | 发票 Id / 类型 / 代码 / 号码 / **身份文案** / 开票日期 / 状态 / 状态文案 / **含税总额** |
| 供应商快照 | 供应商 Id + 编码 + 名称（服务端写入；供应商停用 / 删除后历史证据仍可读，绝不回填） |
| 引用金额 | 原币（与付款单 / 发票币种一致），`DECIMAL(18,2)`；**按币种精度取整后必须大于 0** |
| 备注 | 有界（≤ 500 字符），只作为登记说明，不参与任何金额派生 |
| 登记人 | **服务端**从当前登录账号写入（≤ 100 字符；缺失记「未知用户」）——客户端**不能**提交登记人与任何审计字段 |
| 状态 | `1` 有效 / `2` 已作废（作废 = 保留原始值 + 作废时间 + 作废原因） |

**币种精度**复用仓库唯一权威实现 `CurrencyAmountRules`（与装柜费用分摊 ERP-042、供应商发票 ERP-043、
付款引用 ERP-049 同一套）：

- 无小数币种（JPY / KRW / VND / IDR）为 **0 位**，其余（含未知币种口径）为 **2 位**；
- 取整一律 **0.5 进位**（`MidpointRounding.AwayFromZero`，不使用银行家舍入）；
- **原币存储**：不做汇率换算、不跨币种合并、不按金额相近猜测发票；
- 付款单币种不在系统币种口径内（`CNY / USD / EUR / HKD / GBP / JPY`）时，登记新引用一律拒绝。

## 3. 权威资格与金额校验（服务端）

登记一行引用时按下列顺序校验，任一不满足即拒绝并给出可读原因（**不静默合并、不自动调整**）：

| 校验 | 口径 |
|---|---|
| 付款单存在 | 付款单不存在 / 已删除 → 数据不存在（404 语义） |
| 币种口径 | 付款单币种必须在系统币种口径内（否则无任何发票可以权威匹配） |
| 引用金额 | 按币种精度取整后必须 **> 0**（例如 JPY 的 100.6 → 101；0.004 CNY → 拒绝） |
| 发票存在 / 未删除 | 不存在 / 已删除 → 数据不存在（404 语义） |
| 发票已登记 | 草稿（未登记）与已作废发票**不能**登记引用（历史引用仍可读） |
| 供应商一致 | 发票供应商 Id 必须等于付款单供应商 Id（**不转换、不改派**） |
| 币种一致 | 发票币种必须等于付款单币种（**不做汇率换算**） |
| 单付款单行数上限 | 有效发票引用行最多 50 条（保证视图与前端有界） |
| 重复有效引用 | 同一付款单 + 同一采购发票只允许**一条有效引用行**（重复提交 → 数据重复语义） |
| 付款单金额上限 | **本付款单内有效行金额合计不得超过付款单金额**（已作废行不占用额度） |
| 单发票行数上限 | 单张发票的有效付款引用行最多 50 条 |
| 发票含税总额上限 | **本发票内有效行金额合计不得超过发票含税总额**（已作废行不占用额度） |

> 付款单与发票都可以部分或全部未被引用：未引用金额 / 未引用含税总额只作为派生值展示，
> **不会**被系统改派给任何发票或付款单。发票候选的「剩余未引用」（含税总额 − 本付款单已引用 −
> 其他付款单已引用，下限 0）同样是**派生展示**，不是应付余额、账龄或付款依据。

## 4. 作废与历史（不可硬删除）

- 作废必须填写**原因**（必填、≤ 500 字符），写入 `VoidedAt` / `VoidReason`；
- 作废**保留**原始引用金额、付款单 / 供应商 / 采购发票快照、登记人与审计历史，**不物理删除、不改派、不静默替换**；
- **重复作废被拒绝**；已作废行不再占用额度，因此**同一发票可以重新登记**一条新的有效引用行（新旧并存可查）；
- 控制器**刻意不提供** `PUT` / `PATCH` / `DELETE`：更正只有「作废 + 重新登记」一条可追溯路径；
- 有效行唯一性的数据库兜底是过滤唯一索引 `UX_SupplierPaymentInvoiceAllocations_PaymentInvoice`
  （`IsDeleted = 0 AND Status <> 2`），与模型配置同名同过滤条件。

## 5. 只读派生（付款单侧 / 发票侧汇总与候选）

| 视图 | 口径 |
|---|---|
| 付款单侧汇总 | 付款单快照 + **有效行**已引用金额 / 未引用金额（下限 0）/ 有效行数 / 已作废行数 + 有界逐行明细；已作废历史**永不并入**有效合计，只单独计数与列出 |
| 发票侧汇总 | 发票快照 + **全部有效引用行**（任意付款单）已引用金额 / 未引用含税总额（下限 0）/ 行数 / 已作废行数 + 有界逐行明细 |
| 引用状态 | `unallocated` 未被引用 / `partial` 部分引用 / `fully_allocated` 已全额引用（等于比较基准时才是全额） |
| 可引用付款单候选 | 只列**未删除**付款单（可按供应商筛选 / 付款单号检索，单次 ≤ 200 条），附**发票引用**已引用 / 未引用金额与资格文案 |
| 可引用发票候选 | 只列**同供应商 + 同币种**的未删除发票（单次 ≤ 200 条），含草稿 / 已作废发票并显式标注不可引用；附含税总额、本付款单已引用、其他付款单已引用与剩余未引用（下限 0） |
| 台账 | 分页（默认 50 / 上限 200 条），可按付款单 / 发票 / 供应商 / 状态 / 币种 / 登记时间区间 / 关键字过滤；默认包含已作废历史 |

**查询有界、无逐行查库**：台账每页只做「列表 1 次 + 付款单 1 次 + 发票 1 次」批量装载；
付款单候选为「付款单 1 次 + 有效引用行 1 次 + 供应商 1 次」；发票候选为「发票 1 次 + 有效引用行 1 次」；
付款单汇总为「分组统计 1 次 + 采购订单维度分组统计 1 次 + 明细 1 次 + 批量装载」；
发票侧汇总为「分组统计 1 次 + 明细 1 次 + 批量装载」，与页大小、单据数量无关。

## 6. 证据维度分离（重要：三个维度互不合并）

系统里现在并存三个**彼此独立**的引用 / 关联证据维度：

| 维度 | 表 | 含义 |
|---|---|---|
| 付款 → 采购订单（ERP-049） | `SupplierPaymentAllocations` | 这张付款单把多少钱指向了哪几张采购订单 |
| 付款 → 采购发票（ERP-066，本册） | `SupplierPaymentInvoiceAllocations` | 这张付款单把多少钱指向了哪几张已登记采购发票 |
| 发票 → 采购订单（ERP-043） | `PurchaseInvoiceAllocations` | 这张发票的含税总额关联到哪几张采购订单 |

规则：

- 三个维度**绝不互相回写**，也**绝不把不同维度的金额相加**后当成第二笔付款、已付款金额或应付余额；
- 付款单侧汇总**分别展示**发票引用金额（本册）与采购订单引用金额（ERP-049，只读派生对照值），
  并在响应中附带口径文案 `separateEvidenceText` 与界面提示「分别记录、绝不相加」；
- 三个维度都只是**证据展示**：都不代表已付款、已核销、已认证 / 抵扣或账龄。

## 7. 非变更边界（登记 / 作废都不改写既有数据）

- **付款单**：状态、金额、币种、付款方式、银行账户、供应商、备注、软删除标记**全部不变**（本册只读它）；
- **供应商采购发票**：类型、代码、号码、开票日期、到期日、付款条件、净额 / 税额 / 含税总额、状态、
  发票→采购订单关联行、备注**全部不变**；
- **采购订单**：状态、到货进度、已收数量、金额与明细、结算进度**全部不变**；
- **ERP-049 采购订单引用行**、**库存与库存成本**、**库存流水**、**退税记录**、**费用单**、
  **供应商余额 / 结算方式**：不受影响，也**没有任何请求期回填**；
- 登记 / 作废**不执行任何付款、记账、核销、认证或结算动作**，也不生成任何财务单据。

## 8. 数据库与幂等升级

`SupplierPaymentInvoiceAllocations` 由三处保持一致：

1. **EF 模型**（`ErpDbContext.Config.cs`，ERP-066 段）：长度 / 精度（`DECIMAL(18,2)`）、
   过滤唯一索引 `UX_SupplierPaymentInvoiceAllocations_PaymentInvoice`、付款单 / 发票 / 状态索引；
2. **幂等升级**（`SchemaUpgrader.cs` 第 41 段）：`IF OBJECT_ID(...) IS NULL` 建表 +
   `IF NOT EXISTS (sys.indexes ...)` 建索引，**不含任何 UPDATE / INSERT / DELETE**；
3. **DbSet 与接口**（`ErpDbContext.Entities.cs` / `IErpDbContext.cs`）各新增一个 `DbSet`。

关键设计：

- **刻意不建任何外键**（付款单与发票只做软删除、供应商可能被停用 / 改名）：本表只保存服务端快照，
  历史引用证据必须始终可读，也不参与付款单、发票、采购订单与 ERP-049 采购订单引用行的任何计算；
- 既有付款单、采购发票、采购订单与供应商表**没有任何列变更**，因此历史单据在不登记任何引用时行为与升级前完全一致；
- 生产库结构执行仍由 Human Gate 控制：本任务只产出代码与幂等升级，**不执行任何生产 SQL**。

## 9. 接口一览（`api/supplier-payment-invoice-allocations`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/supplier-payment-invoice-allocations` | 引用行台账（分页、过滤；默认含已作废历史） |
| GET | `/api/supplier-payment-invoice-allocations/{id}` | 引用行详情（含付款单 / 发票可用性只读标注） |
| GET | `/api/supplier-payment-invoice-allocations/payments` | 可引用付款单候选（只读有界，含已引用 / 未引用与资格文案） |
| GET | `/api/supplier-payment-invoice-allocations/payments/{paymentId}/summary` | 付款单侧汇总（含独立标注的 ERP-049 采购订单引用维度） |
| GET | `/api/supplier-payment-invoice-allocations/payments/{paymentId}/allocations` | 指定付款单的引用行清单（只读有界；可按状态筛选） |
| GET | `/api/supplier-payment-invoice-allocations/payments/{paymentId}/invoice-candidates` | 可引用采购发票候选（同供应商 + 同币种，只读有界） |
| GET | `/api/supplier-payment-invoice-allocations/invoices/{purchaseInvoiceId}/summary` | 发票侧汇总（已引用 / 未引用含税总额 + 有界明细） |
| GET | `/api/supplier-payment-invoice-allocations/invoices/{purchaseInvoiceId}/allocations` | 指定发票的引用行清单（只读有界；可按状态筛选） |
| POST | `/api/supplier-payment-invoice-allocations` | 登记引用行（付款单 Id + 发票 Id + 金额 + 备注；登记人取当前账号） |
| POST | `/api/supplier-payment-invoice-allocations/{id}/void` | 作废引用行（原因必填，保留原始值与历史） |

> 没有 `PUT` / `PATCH` / `DELETE`：不提供改派与静默替换已登记金额的能力。

前端入口：`wwwroot/js/supplier-payment-invoice-allocations.js`，注册在 `index.html`；
菜单入口为采购订单模块工具栏 / 行操作「🧾 付款发票引用」（`modules-doc.js`）与付款单模块工具栏
「🧾 付款发票引用」（`modules-finance.js`）。从采购订单行操作进入时会按该单的**供应商**预筛选台账与付款单候选。
