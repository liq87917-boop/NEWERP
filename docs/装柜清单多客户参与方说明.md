# 装柜清单多客户参与方说明（ERP-041）

## 1. 背景与定位

装柜清单（`ContainerLoadingList`）原来只有单个 `CustomerId`，无法表达拼柜（一柜多客户）场景下「这柜装了哪几个客户、哪个是主客户」。

本次新增装柜清单下的**可选子表** `ContainerLoadingListParticipants`（零到多条）：把一个既有装柜清单与**多个既有客户**关联起来，并显式指定其中一条为**主参与方**。

定位：**客户归属清单**。它由人工维护，只描述客户归属与主客户，属于操作性记录：

- 不是费用分摊结果，不是结算单，不是应收应付台账；
- 不参与任何自动决策（不按数量 / 体积 / 重量 / 金额替客户分摊，也不生成任何单据）。

## 2. 表结构

| 项 | 口径 |
|---|---|
| 表 | `ContainerLoadingListParticipants`（`SchemaUpgrader` 第 29 段 `IF OBJECT_ID(...) IS NULL` 幂等建表） |
| 列 | `LoadingListId`、`CustomerId` BIGINT；`CustomerCode` NVARCHAR(50)、`CustomerName` NVARCHAR(200)（服务端权威写入的客户快照）；`IsPrimary` BIT；`Status` INT（1 启用 / 0 停用）；`SortOrder` INT；`Remark` NVARCHAR(500) + 审计基类字段 |
| 客户快照 | `CustomerCode` / `CustomerName` 一律由服务端按客户主数据写入，客户端提交值不被采信；客户后来停用 / 删除 / 改名时快照保留，界面显式标注「（已停用/不可用）」并单独暴露客户当前名称与差异 |
| 引用校验 | 新增 / 更换客户：必须存在、未删除、**启用**（不存在或已删除 → 未找到；已停用 → 参数校验失败，历史参与方仍可读） |
| 唯一约束 | `UX_ContainerLoadingListParticipants_ListCustomer`（`LoadingListId, CustomerId` WHERE `IsDeleted = 0`）＝ 同一清单内同一客户不重复（软删除行不占用，**停用的历史行仍占用**，恢复参与应直接启用原参与方）；`UX_ContainerLoadingListParticipants_ListPrimary`（`LoadingListId` WHERE `IsDeleted = 0 AND Status = 1 AND IsPrimary = 1`）＝ 同一清单最多一条**启用中**主参与方；另建 `IX_ContainerLoadingListParticipants_CustomerId` 供客户侧有界检索 |
| 有界列表 | 单清单参与方上限 **100 条**（含停用行）；列表 / 维护视图按上限收敛，超上限的新增被拒绝 |
| 主参与方口径 | 同一清单最多一条启用主参与方；**更换主参与方必须显式调用「设为主参与方」**：服务端先在同一清单内释放旧主参与方（一次批量写回），再置新主参与方并把装柜清单的兼容客户字段同步为该客户 —— 与列表顺序无关，也不依赖「最后提交者胜出」 |
| 停用 / 删除主参与方 | **只有在本清单不再有其他启用参与方时**才允许：此时清单回退为按兼容字段读取的**历史单客户视图**，兼容字段保留原值（不清空）；否则必须先显式改指其他参与方。直接取消主参与方标记（`isPrimary=false`）会被拒绝 |
| 软删除 | `DELETE` 只做本表软删除（历史行保留可读、同时释放主标记）；软删除行不占用「同清单同一客户」唯一位，因此同一客户可在保留历史行的前提下重新新增 |
| 边界 | 本子表**不建数据库外键、不被任何单据引用**：不按数量 / 体积 / 金额分摊费用、不生成费用单或结算单，不改写装柜明细（数量 / 箱数 / 重量 / 体积）、柜号、订柜信息的外贸与物流跟踪值、单证 `TradeDocuments`、库存 `Stocks` / 库存流水 `StockMovements`、出口退税与客户主数据，也不调用任何外部系统 |

## 3. 兼容客户字段与历史数据

| 项 | 口径 |
|---|---|
| 兼容字段 | 装柜清单原有 `CustomerId` 保留为**兼容主客户字段**：只有「显式指定主参与方」时服务端才把它同步为该客户（与参与方同批保存）；其余维护动作（编辑备注、停用非主参与方等）不改写它 |
| 历史清单 | 没有任何参与方行的历史装柜清单行为完全不变：客户归属只按 `CustomerId` 读取，服务端在读取标注中显式标记 `legacySingleCustomer = true`，界面按「历史单客户视图」说明 |
| 无回填 | 建表与读取**不做任何回填**；读取请求不写库（无请求时写入、无自动补参与方行） |
| 不可用引用 | 参与方的客户被停用 / 删除后：历史参与方照常可读（快照显示原编码 / 名称 + 显式标注不可用），但**不能被新选为主参与方**，也不能被重新启用（重新启用等同于重新选用该客户） |

## 4. 可维护性与单据状态

- **只有已作废（Cancelled）**的装柜清单禁止维护参与方（作废柜的客户归属必须冻结），此时历史参与方仍可只读查看与导出说明。
- 其余状态（待提交 / 已提交 / 已审核 / 已完成）都允许维护：参与方是**操作性的客户归属清单**，拼柜客户在出运前后都可能需要补充或纠正；它唯一会写到的装柜清单字段，是任务明确要求的兼容主客户字段 `CustomerId`，且只在「显式指定主参与方」时同步 —— 不改写柜号、装柜明细、订柜跟踪值、单证、费用、库存与客户主数据。
- 读取（参与方列表、装柜清单列表与详情标注）在**任何状态**都可用，包括已作废清单的历史参与方。
- 跨清单访问被拒绝：参与方只能通过它所属的装柜清单路径访问（`{id}/participants/{participantId}`）。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/container/loading-lists/{id}/participants?activeOnly=` | 只读、有界；默认含停用参与方（历史可读），`activeOnly=true` 只返回启用中的参与方 |
| POST | `/api/container/loading-lists/{id}/participants` | 新增参与方（客户必须启用；同清单同一客户不重复；`isPrimary=true` 时清单不得已有启用主参与方） |
| PUT | `/api/container/loading-lists/{id}/participants/{participantId}` | 修改参与方（更换客户重新校验；引用未变更时保留历史快照；`isPrimary=true` 视为显式置主） |
| POST | `/api/container/loading-lists/{id}/participants/{participantId}/primary` | 显式设为主参与方（先释放旧主，再同步兼容客户字段） |
| POST | `/api/container/loading-lists/{id}/participants/{participantId}/disable` | 停用参与方（历史仍可读；停用当前主参与方要求清单不再有其他启用参与方） |
| POST | `/api/container/loading-lists/{id}/participants/{participantId}/enable` | 重新启用（客户必须仍可用；不会自动恢复主参与方标记） |
| DELETE | `/api/container/loading-lists/{id}/participants/{participantId}` | 软删除（历史行保留；不改写任何相邻数据） |

装柜清单的列表与详情响应附以下**只读标注**（`[NotMapped]`，不落库，一次批量查询解析、无逐行查询）：

`participantCount`（启用数）、`participantTotalCount`（含停用总数）、`primaryParticipantCustomerId`、`primaryParticipantCustomerName`、`primaryParticipantAvailable`、`legacySingleCustomer`。

## 6. 界面

- 装柜清单列表新增「客户参与方」列：0 条显示「—（单客户）」；有参与方时显示「启用数 / 总数」、停用条数与主参与方（主客户不可用时带显式标注）。
- 行操作「多客户参与方」打开维护弹窗：参与客户下拉（只列启用客户）、主参与方、排序号、备注；列表行支持编辑 / 设为主参与方 / 停用 / 启用 / 删除；已作废清单的行按钮禁用并给出状态说明（其余状态可维护）。
- 弹窗文案明确：本视图只维护客户归属，不按数量 / 体积 / 金额分摊费用，不生成费用单，也不改动装柜明细、柜号、物流跟踪值、单证、库存与客户主数据。
- 前端脚本：`wwwroot/js/loading-list-participants.js`，脚本注册于 `wwwroot/index.html`，模块列与行操作登记在 `modules-doc2.js` 的 `loading-list` 配置。

## 7. 边界（明确不做）

1. 不分摊费用：按箱数 / 体积 / 重量 / 金额分摊与分摊批次留痕是**独立任务**，本表只提供参与客户清单；
2. 不改写装柜清单明细数量 / 箱数 / 重量 / 体积、柜号、预装柜单引用；
3. 不改写订柜信息（`ContainerBooking`）的外贸与物流跟踪值（ERP-040 的只读回显链路口径不变）；
4. 不改写单证、库存、库存流水、出口退税与客户主数据；
5. 不调用船公司 / 海关 / 货代等外部系统；
6. 不建数据库外键，不做历史数据修补：客户软删除 / 停用不影响历史参与方读取。

## 8. 结构与验证

- 建表与索引由 `SchemaUpgrader` 第 29 段幂等补齐（`IF OBJECT_ID(...) IS NULL` + `IF NOT EXISTS (SELECT 1 FROM sys.indexes ...)`），**不做任何回填**，也不改写任何其他表；
- 生产库执行、历史数据迁移、部署与发布仍受 **Human Gate** 控制；本文档不声明生产库已升级；
- 单元测试：`ERP.UnitTests/ContainerLoadingParticipantTests.cs`（多客户、重复与引用校验、主参与方唯一与显式转移、兼容字段同步、历史单客户视图与读取不写库、不可用引用、有界上限、已作废柜只读 / 已审核柜可维护、非改写相邻数据、模型 / 幂等结构 / 前端接线契约）；
- 真实 Edge 浏览器验收按项目策略记为 `browser_deferred`，统一延后到 `FINAL-UI-ACCEPTANCE` 阶段。
