# 供应商付款关联采购订单说明（ERP-049）

## 1. 背景与定位

系统里已经有供应商**付款单**（`FinancePayment`，含付款单号 / 日期 / 供应商 / 金额 / 币种 / 付款方式 / 银行账户 / 状态），
ERP-026（采购订单执行进度）与 ERP-028（财务核对）也能按既有引用字段把付款单与采购订单「关联起来看」，
但这些都只是**派生展示**：用户没有办法**显式登记**「这笔付款到底对应哪几张采购订单」，也就无法在
「一笔付款拆给多张订单」或「引用录错需要更正」时留下可追溯的痕迹。

本次（ERP-049）新增**供应商付款引用登记册**（`SupplierPaymentAllocations`）：

- 在**既有、未删除**的付款单之上登记引用（分摊）行：一行 = 一张付款单 → 一张采购订单 + 一个引用金额；
- 引用只按**权威一致性**（同供应商 + 同币种、订单未取消）建立，**不按单号相似度、金额相近、日期接近猜测订单**；
- 付款单侧显式展示**已引用 / 未引用金额**，未引用金额绝不被猜测到任何订单；
- 更正走**显式作废**（必填原因）：保留原始金额、快照与历史，不提供硬删除与静默替换。

定位：**付款引用证据登记册**。它**不是**银行付款凭证、**不是**应付账款核销、**不是**发票核销、
**不是**税务（进项）抵扣判断，也**不是**供应商余额。登记 / 作废一行都**不会真的付款、不会移动资金、
不会把发票或采购订单标记为已结清**，也不引入第二套账务引擎（不记账、不生成凭证 / 收付款 / 结算单）。

> 本说明对应改动**不含**任何历史数据回填，也**不新增或修改付款单与采购订单的任何列**；
> 新增的只有 `SupplierPaymentAllocations` 一张表（幂等建表 + 索引，见第 7 节）。

## 2. 字段与快照口径

| 字段 | 口径 |
|---|---|
| 付款单 | 必须**存在且未删除**（付款单状态不限；本册不改变付款单状态，只保存写入时的状态快照） |
| 付款单快照 | 单号 / 付款日期 / 状态 / 状态文案 / **付款金额**（原币，写入时取自付款单，作为有效行金额合计上限） |
| 采购订单 | 必须**存在、未删除、未取消**；供应商与币种都必须与付款单**一致** |
| 订单快照 | 采购单号 / 订单日期 / 订单状态 / 订单币种 |
| 供应商快照 | 供应商 Id + 编码 + 名称（服务端写入；供应商停用 / 删除后历史证据仍可读，绝不回填） |
| 引用金额 | 原币（与付款单币种一致），`DECIMAL(18,2)`；**按币种精度取整后必须大于 0** |
| 备注 | 有界（≤ 500 字符），只作为登记说明，不参与任何金额派生 |
| 状态 | `1` 有效 / `2` 已作废（作废 = 保留原始值 + 作废时间 + 作废原因） |

**币种精度**复用仓库唯一权威实现 `CurrencyAmountRules`（与装柜费用分摊 ERP-042、供应商发票 ERP-043 同一套）：

- 无小数币种（JPY / KRW / VND / IDR）为 **0 位**，其余（含未知币种口径）为 **2 位**；
- 取整一律 **0.5 进位**（`MidpointRounding.AwayFromZero`，不使用银行家舍入）；
- **原币存储**：不做汇率换算、不跨币种合并、不按金额相近猜测订单；
- 付款单币种不在系统币种口径内（`CNY / USD / EUR / HKD / GBP / JPY`）时，登记新引用一律拒绝。

## 3. 权威资格与金额校验（服务端）

登记一行引用时按下列顺序校验，任一不满足即拒绝并给出可读原因（**不静默合并、不自动调整**）：

| 校验 | 口径 |
|---|---|
| 付款单存在 | 付款单不存在 / 已删除 → 数据不存在（404 语义） |
| 币种口径 | 付款单币种必须在系统币种口径内（否则无任何订单可以权威匹配） |
| 引用金额 | 按币种精度取整后必须 **> 0**（例如 JPY 的 100.6 → 101；0.004 CNY → 拒绝） |
| 订单存在 / 未删除 | 不存在 / 已删除 → 数据不存在（404 语义） |
| 订单未取消 | 已取消订单**不能**登记引用（历史引用仍可读） |
| 供应商一致 | 订单供应商 Id 必须等于付款单供应商 Id（**不转换、不改派**） |
| 币种一致 | 订单币种必须等于付款单币种（**不做汇率换算**） |
| 单付款单行数上限 | 有效引用行最多 50 条（保证视图与前端有界） |
| 重复有效引用 | 同一付款单 + 同一采购订单只允许**一条有效引用行**（重复提交 → 数据重复语义） |
| 付款金额上限 | **有效行金额合计不得超过付款单金额**（已作废行不占用额度） |

> 付款单可以部分或全部未被引用：未引用金额只作为派生值展示，**不会**被系统改派给任何订单。
> 采购订单侧的「剩余未覆盖金额」（订单总额 − 本单已引用 − 其他付款单已引用）同样是**派生展示**，
> 不是应付余额、账龄或结算依据，也不是引用金额的硬上限。

## 4. 作废与历史（不可硬删除）

- 作废必须填写**原因**（必填、≤ 500 字符），写入 `VoidedAt` / `VoidReason`；
- 作废**保留**原始引用金额、付款单 / 供应商 / 采购订单快照与审计历史，**不物理删除、不静默替换**；
- **重复作废被拒绝**；已作废行不再占用付款金额额度，因此**同一订单可以重新登记**一条新的有效引用行（新旧并存可查）；
- 有效行唯一性的数据库兜底是过滤唯一索引 `UX_SupplierPaymentAllocations_PaymentOrder`
  （`IsDeleted = 0 AND Status <> 2`），与模型配置同名同过滤条件。

## 5. 只读派生（付款单侧汇总与候选）

| 视图 | 口径 |
|---|---|
| 付款单侧汇总 | 付款单快照 + **有效行**已引用金额 / 未引用金额（下限 0）/ 有效行数 / 已作废行数 + 有界逐行明细；已作废历史**永不并入**有效合计，只单独计数与列出 |
| 引用状态 | `unallocated` 未被引用 / `partial` 部分引用 / `fully_allocated` 已全额引用（等于付款金额时才是全额） |
| 可引用付款单候选 | 只列**未删除**付款单（可按供应商筛选 / 付款单号检索，单次 ≤ 200 条），附已引用 / 未引用金额与资格文案（已占满 / 币种不受支持 → 不可引用） |
| 可引用采购订单候选 | 只列**同供应商 + 同币种**的未删除订单（单次 ≤ 200 条），含已取消订单并显式标注不可引用；附订单总额、本付款单已引用、其他付款单已引用与剩余未覆盖（下限 0） |
| 台账 | 分页（默认 50 / 上限 200 条），可按付款单 / 采购订单 / 供应商 / 状态 / 币种 / 登记时间区间 / 关键字过滤；默认包含已作废历史 |

**查询有界、无逐行查库**：台账每页只做「列表 1 次 + 付款单 1 次 + 采购订单 1 次」批量装载；
付款单候选为「付款单 1 次 + 有效引用行 1 次 + 供应商 1 次」；订单候选为「订单 1 次 + 有效引用行 1 次 + 供应商 1 次」；
付款单汇总为「汇总 1 次 + 明细 1 次 + 批量装载」，与页大小、单据数量无关。

## 6. 非变更边界（登记 / 作废都不改写既有数据）

- **付款单**：状态、金额、币种、付款方式、银行账户、供应商、备注、软删除标记**全部不变**（本册只读它）；
- **采购订单**：状态、到货进度、已收数量、金额与明细、结算进度、供应商确认交期**全部不变**；
- **发票与发票关联**（ERP-043 / ERP-044 / ERP-048）、**库存与库存成本**、**库存流水**、**退税记录**、
  **费用单**、**供应商余额 / 结算方式**：不受影响，也**没有任何请求期回填**；
- 登记 / 作废**不执行任何付款、记账、核销或结算动作**，也不生成任何财务单据。

## 7. 数据库与幂等升级

`SupplierPaymentAllocations` 由三处保持一致：

1. **EF 模型**（`ErpDbContext.Config.cs`，ERP-049 段）：长度 / 精度（`DECIMAL(18,2)`）、
   过滤唯一索引 `UX_SupplierPaymentAllocations_PaymentOrder`、订单与状态索引；
2. **幂等升级**（`SchemaUpgrader.cs` 第 34 段）：`IF OBJECT_ID(...) IS NULL` 建表 +
   `IF NOT EXISTS (sys.indexes ...)` 建索引，**不含任何 UPDATE / INSERT / DELETE**；
3. **DbSet 与接口**（`ErpDbContext.Entities.cs` / `IErpDbContext.cs`）各新增一个 `DbSet`。

关键设计：

- **刻意不建任何外键**（付款单只做软删除；采购订单与供应商可能被软删除 / 取消 / 改名）：
  本表只保存服务端快照，历史引用证据必须始终可读，也不参与付款单与采购订单的任何计算；
- 既有付款单、采购订单、供应商表**没有任何列变更**，因此历史单据在不登记任何引用时行为与升级前完全一致；
- 生产库结构执行仍由 Human Gate 控制：本任务只产出代码与幂等升级，**不执行任何生产 SQL**。

## 8. 接口一览（`api/supplier-payment-allocations`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/supplier-payment-allocations` | 引用行台账（分页、过滤；默认含已作废历史） |
| GET | `/api/supplier-payment-allocations/{id}` | 引用行详情（含付款单 / 订单可用性只读标注） |
| GET | `/api/supplier-payment-allocations/payments` | 可引用付款单候选（只读有界，含已引用 / 未引用与资格文案） |
| GET | `/api/supplier-payment-allocations/payments/{paymentId}/summary` | 付款单侧汇总（有效行已引用 / 未引用 / 行数 + 有界明细） |
| GET | `/api/supplier-payment-allocations/payments/{paymentId}/allocations` | 指定付款单的引用行清单（只读有界；可按状态筛选） |
| GET | `/api/supplier-payment-allocations/payments/{paymentId}/order-candidates` | 可引用采购订单候选（同供应商 + 同币种；只读有界） |
| POST | `/api/supplier-payment-allocations` | 登记一条引用行（全部服务端校验） |
| POST | `/api/supplier-payment-allocations/{id}/void` | 作废引用行（必填原因；保留历史） |

响应统一为 `ApiResponse<T>`（`code / message / data`）；提示文案中明确「仅证据留痕；未执行付款、未结算、未核销」。

## 9. 前端入口与界面

- **付款单列表**（账务管理 → 付款单，`modules-finance.js`）：工具栏「💳 付款引用」打开登记册；
- **采购订单列表**（`modules-doc.js`）：工具栏「💳 付款引用」打开登记册；
  行操作「付款引用」按该采购单预筛选台账（只显示指向本单的引用行）；
- **登记册页面**（`wwwroot/js/supplier-payment-allocations.js`，由 `index.html` 引入）：

| 视图 | 内容 |
|---|---|
| 台账 | 状态 / 币种 / 登记日期区间 / 关键字过滤、分页、详情与作废按钮 |
| 按付款单登记引用 | 选择付款单 → 展示付款金额、已引用 / 未引用、引用状态；候选订单表（可否引用 + 引用金额 + 备注 + 单行「登记引用」按钮）；下方列出本付款单的引用行（含已作废历史） |
| 详情 / 作废 | 逐字段快照与可用性文案；作废必须填原因，明确「保留历史、不物理删除、不会撤销任何真实付款」 |

界面与服务端文案同源：所有提示都明确本册**不是**付款凭证 / 应付账款核销 / 发票核销 / 税务判断 / 供应商余额。
