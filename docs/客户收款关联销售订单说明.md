# 客户收款关联销售订单说明（ERP-053）

## 1. 背景与定位

系统里已经有客户**收款单**（`FinanceReceipt`，含收款单号 / 日期 / 客户 / 金额 / 币种 / 付款方式 / 银行账户 / 状态），
ERP-032（销售订单出货 / 财务进度报表）与 ERP-046（客户订单与收款核对报表）也能把收款单与销售订单
「放在一起看」，但它们的权威口径是：**收款单只记录客户（`SalesOrderProgress.ReferenceReceipt = FinanceReceipt.CustomerId`），
没有订单级持久化引用**，因此历史收款证据在订单侧只能作为「未关联证据」单独列出，绝不按客户名、订单号文本、
日期或金额相似度猜测链接。用户没有任何办法**显式登记**「这笔收款到底对应哪几张销售订单」，
也就无法在「一笔收款拆给多张订单」或「引用录错需要更正」时留下可追溯的痕迹。

**ERP-053 的审计结论（对应验收项 2）**：
`FinanceReceipt` 与 `SalesOrder` 两侧都**不存在**任何订单级 / 收款级持久化引用列，
`SchemaUpgrader` 中也不存在第二套收款 → 订单链接结构，因此**没有可复用的既有权威关系**；
本任务只新建**一套**权威引用册，不建立竞争模型。审计结论由
`ERP.UnitTests/CustomerReceiptAllocationTests.cs` 的
`ERP032审计_收款单只有客户级引用_仓库只有一套收款引用模型` 用例以源码 / 反射 + 模型契约方式锁定：

- `SalesOrderProgress.ReferenceReceipt = "FinanceReceipt.CustomerId"` 与
  「收款单 / 装柜结算单 / 散货结算单只记录客户，没有订单级引用」的既有口径保持不变；
- ERP-046 的 `UnlinkedReferenceField` 仍直接引用该常量（不新增第二套口径）；
- `FinanceReceipt` 上没有 `SalesOrderId` / `OrderNo`，`SalesOrder` 上没有 `Receipt*` 列；
- 幂等升级只建 `CustomerReceiptAllocations` 一张表，本模块段落内**不含任何 `ALTER TABLE`**；
- `IErpDbContext` 中只有一套「收款引用」模型（`CustomerReceiptAllocations`）。

本次（ERP-053）新增**客户收款引用登记册**（`CustomerReceiptAllocations`）：

- 在**既有、未删除**的收款单之上登记引用（分摊）行：一行 = 一张收款单 → 一张销售订单 + 一个引用金额；
- 引用只按**权威一致性**（同客户 + 同币种、订单未取消）建立，**不按单号相似度、金额相近、日期接近猜测订单**；
- 收款单侧显式展示**已引用 / 未引用金额**，未引用金额绝不被猜测到任何订单，也不代表应收未收余额；
- 更正走**显式作废**（必填原因）：保留原始金额、快照与历史，不提供硬删除与静默替换。

定位：**收款引用证据登记册**。它**不是**银行入账 / 到账凭证、**不是**应收账款台账或余额、
**不是**货款核销、**不是**客户对账单（statement of account）、**不是**税务（销项）判断，
也**不构成**任何法律上的债务清偿或客户信用结论。登记 / 作废一行都**不会真的收款、不会移动资金、
不会把销售订单标记为已收款或已结清**，也不引入第二套账务引擎（不记账、不生成凭证 / 收款 / 结算单、
不改写客户信用额度或信用状态）。

> 本说明对应改动**不含**任何历史数据回填，也**不新增或修改收款单与销售订单的任何列**；
> 新增的只有 `CustomerReceiptAllocations` 一张表（幂等建表 + 索引，见第 7 节）。

## 2. 字段与快照口径

| 字段 | 口径 |
|---|---|
| 收款单 | 必须**存在且未删除**（收款单状态不限；本册不改变收款单状态，只保存写入时的状态快照） |
| 收款单快照 | 单号 / 收款日期 / 状态 / 状态文案 / **收款金额**（原币，写入时取自收款单，作为有效行金额合计上限） |
| 销售订单 | 必须**存在、未删除、未取消**；客户与币种都必须与收款单**一致** |
| 订单快照 | 销售订单号 / 订单日期 / 订单状态 / 订单币种 |
| 客户快照 | 客户 Id + 编码 + 名称（服务端写入；客户停用 / 删除后历史证据仍可读，绝不回填） |
| 引用金额 | 原币（与收款单币种一致），`DECIMAL(18,2)`；**按币种精度取整后必须大于 0** |
| 备注 | 有界（≤ 500 字符），只作为登记说明，不参与任何金额派生 |
| 状态 | `1` 有效 / `2` 已作废（作废 = 保留原始值 + 作废时间 + 作废原因） |

**币种精度**复用仓库唯一权威实现 `CurrencyAmountRules`（与装柜费用分摊 ERP-042、供应商发票 ERP-043、
供应商付款引用 ERP-049 同一套）：

- 无小数币种（JPY / KRW / VND / IDR）为 **0 位**，其余（含未知币种口径）为 **2 位**；
- 取整一律 **0.5 进位**（`MidpointRounding.AwayFromZero`，不使用银行家舍入）；
- **原币存储**：不做汇率换算、不跨币种合并、不按金额相近猜测订单；
- 收款单币种不在系统币种口径内（`CNY / USD / EUR / HKD / GBP / JPY`）时，登记新引用一律拒绝。

## 3. 权威资格与金额校验（服务端）

登记一行引用时按下列顺序校验，任一不满足即拒绝并给出可读原因（**不静默合并、不自动调整**）：

| 校验 | 口径 |
|---|---|
| 收款单存在 | 收款单不存在 / 已删除 → 数据不存在（404 语义） |
| 币种口径 | 收款单币种必须在系统币种口径内（否则无任何订单可以权威匹配） |
| 引用金额 | 按币种精度取整后必须 **> 0**（例如 JPY 的 100.6 → 101；0.004 CNY → 拒绝） |
| 订单存在 / 未删除 | 不存在 / 已删除 → 数据不存在（404 语义） |
| 订单未取消 | 已取消订单**不能**登记引用（历史引用仍可读） |
| 客户一致 | 订单客户 Id 必须等于收款单客户 Id（**不转换、不改派**） |
| 币种一致 | 订单币种必须等于收款单币种（**不做汇率换算**） |
| 单收款单行数上限 | 有效引用行最多 50 条（保证视图与前端有界） |
| 重复有效引用 | 同一收款单 + 同一销售订单只允许**一条有效引用行**（重复提交 → 数据重复语义） |
| 收款金额上限 | **有效行金额合计不得超过收款单金额**（已作废行不占用额度） |

> 收款单可以部分或全部未被引用：未引用金额只作为派生值展示，**不会**被系统改派给任何订单，
> 也**不**表示应收未收余额、账龄或催收依据。
> 销售订单侧的「剩余未覆盖金额」（订单总额 − 本单已引用 − 其他收款单已引用）同样是**派生展示**，
> 不是应收余额、信用额度或结算依据，也不是引用金额的硬上限。

## 4. 作废与历史（不可硬删除）

- 作废必须填写**原因**（必填、≤ 500 字符），写入 `VoidedAt` / `VoidReason`；
- 作废**保留**原始引用金额、收款单 / 客户 / 销售订单快照与审计历史，**不物理删除、不静默替换**；
- **重复作废被拒绝**；已作废行不再占用收款金额额度，因此**同一订单可以重新登记**一条新的有效引用行（新旧并存可查）；
- 有效行唯一性的数据库兜底是过滤唯一索引 `UX_CustomerReceiptAllocations_ReceiptOrder`
  （`IsDeleted = 0 AND Status <> 2`），与模型配置同名同过滤条件。

## 5. 只读派生（收款单侧汇总与候选）

| 视图 | 口径 |
|---|---|
| 收款单侧汇总 | 收款单快照 + **有效行**已引用金额 / 未引用金额（下限 0）/ 有效行数 / 已作废行数 + 有界逐行明细；已作废历史**永不并入**有效合计，只单独计数与列出 |
| 引用状态 | `unallocated` 未被引用 / `partial` 部分引用 / `fully_allocated` 已全额引用（等于收款金额时才是全额） |
| 可引用收款单候选 | 只列**未删除**收款单（可按客户筛选 / 收款单号检索，单次 ≤ 200 条），附已引用 / 未引用金额与资格文案（已占满 / 币种不受支持 → 不可引用） |
| 可引用销售订单候选 | 只列**同客户 + 同币种**的未删除订单（单次 ≤ 200 条），含已取消订单并显式标注不可引用；附订单总额、本收款单已引用、其他收款单已引用与剩余未覆盖（下限 0） |
| 台账 | 分页（默认 50 / 上限 200 条），可按收款单 / 销售订单 / 客户 / 状态 / 币种 / 登记时间区间 / 关键字过滤；默认包含已作废历史 |

**查询有界、无逐行查库**：台账每页只做「列表 1 次 + 收款单 1 次 + 客户 1 次 + 销售订单 1 次」批量装载；
收款单候选为「收款单 1 次 + 有效引用行 1 次 + 客户 1 次」；订单候选为「订单 1 次 + 有效引用行 1 次 + 客户 1 次」；
收款单汇总为「分组统计 1 次 + 明细 1 次 + 批量装载」，与页大小、单据数量无关。

## 6. 非变更边界（登记 / 作废都不改写既有数据）

- **收款单**：状态、金额、币种、付款方式、银行账户、客户、备注、软删除标记**全部不变**（本册只读它）；
- **销售订单**：状态、出货进度、金额与明细、定金、交期、合同与报关字段**全部不变**；
- **客户资料**：信用状态（正常 / 预警 / 暂停）、信用额度、账期、结算方式、备注**全部不变**（不因收款引用自动放宽或收紧信用）；
- **发票与发票关联**、**库存与库存成本**、**库存流水**、**装柜与单证记录**、**佣金 / 回佣**、
  **退税记录**、**费用单**、**供应商付款引用**：不受影响，也**没有任何请求期回填**；
- 登记 / 作废**不执行任何收款、记账、核销、结算或催收动作**，也不生成任何财务单据。

## 7. 数据库与幂等升级

`CustomerReceiptAllocations` 由三处保持一致：

1. **EF 模型**（`ErpDbContext.Config.cs`，ERP-053 段）：长度 / 精度（`DECIMAL(18,2)`）、
   过滤唯一索引 `UX_CustomerReceiptAllocations_ReceiptOrder`、收款单 / 订单 / 状态索引；
2. **幂等升级**（`SchemaUpgrader.cs` 第 36 段）：`IF OBJECT_ID(...) IS NULL` 建表 +
   `IF NOT EXISTS (sys.indexes ...)` 建索引，**不含任何 `ALTER TABLE`、UPDATE / INSERT / DELETE**；
3. **DbSet 与接口**（`ErpDbContext.Entities.cs` / `IErpDbContext.cs`）各新增一个 `DbSet`。

关键设计：

- **刻意不建任何外键**（收款单只做软删除；销售订单与客户可能被软删除 / 取消 / 停用 / 改名）：
  本表只保存服务端快照，历史引用证据必须始终可读，也不参与收款单与销售订单的任何计算；
- 既有收款单、销售订单、客户表**没有任何列变更**，因此历史单据在不登记任何引用时行为与升级前完全一致；
- 生产库结构执行仍由 Human Gate 控制：本任务只产出代码与幂等升级，**不执行任何生产 SQL**。

## 8. 接口一览（`api/customer-receipt-allocations`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/customer-receipt-allocations` | 引用行台账（分页、过滤；默认含已作废历史） |
| GET | `/api/customer-receipt-allocations/{id}` | 引用行详情（含收款单 / 订单可用性只读标注） |
| GET | `/api/customer-receipt-allocations/receipts` | 可引用收款单候选（只读有界，含已引用 / 未引用与资格文案） |
| GET | `/api/customer-receipt-allocations/receipts/{receiptId}/summary` | 收款单侧汇总（有效行已引用 / 未引用 / 行数 + 有界明细） |
| GET | `/api/customer-receipt-allocations/receipts/{receiptId}/allocations` | 指定收款单的引用行清单（只读有界；可按状态筛选） |
| GET | `/api/customer-receipt-allocations/receipts/{receiptId}/order-candidates` | 可引用销售订单候选（同客户 + 同币种；只读有界） |
| POST | `/api/customer-receipt-allocations` | 登记一条引用行（全部服务端校验） |
| POST | `/api/customer-receipt-allocations/{id}/void` | 作废引用行（必填原因；保留历史） |

## 12. 订单侧收款引用证据（ERP-054）

ERP-053 只提供了登记册（收款单维度 + 台账）。ERP-054 在同一份持久化引用行之上补上**销售订单维度**的
只读证据视图：让使用者从订单出发就能看到「哪些既有收款单把多少钱指向了本单」，同时**不引入第二套匹配、
分桶或对账算法**（复用的正是 ERP-053 的 `CustomerReceiptAllocationRules` / 持久化行与上述分桶口径）。

### 12.1 派生口径（与 ERP-053 / ERP-046 同源）

- 全部金额只按 `CustomerReceiptAllocations` 的**未删除持久化行**派生，且只有**有效（未作废）**行计入有效合计；
- 逐行分桶（`SalesOrderReceiptEvidenceSemantics.SupportedBuckets`）：
  `recorded`（有效：引用行有效、收款单可用、客户 / 币种 / 订单币种快照自相一致、订单可用且与收款单同客户同币种）、
  `voided`（已作废，保留原始金额 / 快照 / 作废原因）、
  `invalid`（客户或币种与收款单不一致、订单币种快照自相矛盾、金额非正数、状态码无法识别 —— 金额原样保留，
  **不换算、不合并、不改派**）、
  `unavailable`（引用行指向的收款单或销售订单不存在 / 已删除 —— 有效性无法确认，不按 0）；
- 汇总字段：有效已引用金额、收款单张数（按收款单去重）、引用行总条数、参与证据的收款单金额快照合计、
  **未指向本单金额**（快照合计 − 有效已引用，下限 0）、**订单金额中未被任何有效引用证据指向的部分**
  （订单金额 − 有效已引用，下限 0）、已作废 / 无效 / 无法确认的条数与金额；
- 未知处理：命中读取上限（或订单不可用 / 已取消）时金额与计数一律为 `null`（未知），**绝不报出部分合计、
  也绝不用 0 顶替**；`unreferencedReceiptAmount` 只表示「这些收款单金额中未指向本单的部分」（可能指向其他订单），
  `unreferencedOrderAmount` 只表示「订单金额中没有任何有效引用证据指向的部分」，**两者都不是应收余额、
  不是未收款金额、不是账龄或催收依据**；
- 有界：详情固定 4 次数据集访问（订单 + 持久化引用行 + 收款单 + 收款单侧有效引用合计聚合，含 1 条溢出探测），
  与订单张数 / 行数无关（无逐行查库 / 无 N+1）；列表批量单次最多 200 张订单、5000 条引用行，
  详情最多 500 条引用行，**全程只读、不写库**。

### 12.2 接口一览（只读 GET）

### 12.4 与 ERP-046 报表的关系（三类证据分列）

ERP-046 报表把三类证据**分开标注**、绝不互加：① 已订 / 已出 / 未出数量（ERP-032 出库单派生）；
② 「已关联收款金额 / 未覆盖金额」（定金 / 货款申请单的 `SalesOrderId` 权威引用，ERP-028 / ERP-032）；
③ **收款引用登记证据**（ERP-053 持久化引用行，ERP-054 新增）。报表仍保持固定 16 次数据集访问
（原 12 次 + 收款引用证据聚合 4 次），命中聚合上限（500 张订单）时一律按未知显示。
