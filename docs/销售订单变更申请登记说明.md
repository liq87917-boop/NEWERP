# 销售订单变更申请登记说明（ERP-047）

> 任务：`ERP-047` 新增**销售订单变更申请登记册**：把「某张既有销售订单希望改成什么」登记为一条带**来源快照**的申请，
> 供人工审阅与留痕。
> 范围：`src/ERP.Domain`、`src/ERP.Application`、`src/ERP.Infrastructure`、`src/ERP.Api`、
> `src/ERP.UnitTests`、`docs/**`。
> 本次**未启动 API、未连接 SQL Server、未执行任何 `.sql` / seed / 部署动作**，验收仅使用本机内存库
> （`ERP.UnitTests`）+ Release 构建（0 警告 0 错误）。

## 1. 定位与边界

**定位**：变更申请是**不可变的拟议变更登记册**——一条申请 = 「来源销售订单在登记当时的样子」+
「申请人希望改成什么」+「提交 / 取消留痕」。它是**人工审阅的输入**，而**不是**销售订单的新版本。

明确**不做**的事（代码、接口与界面同源声明）：

- **不审核、不套用**：没有审批阈值、审批人、生效时间、优先级，也没有「已批准 / 已套用」状态；
  任何变更的批准与执行都要在系统之外由人工决定，并另行走既有销售订单流程；
- **不改写来源销售订单**：创建 / 编辑 / 提交 / 取消申请都不修改 `SalesOrders` / `SalesOrderDetails`
  （只读快照），也不修改 `UpdatedAt`；
- **不改写任何下游**：报价单、销售出库、装柜与出运、收款与发票、佣金、库存与库存成本、
  单证中心与财务记录一律不变；
- **不做生产库动作**：不执行任何 DDL、回填或数据迁移；建表 / 建索引只由 `SchemaUpgrader` 幂等补齐；
- **不硬删除**：更正走「取消 + 原因」，原始与拟议证据保留可读。

## 2. 状态机与不可变口径

| 状态 | 值 | 可编辑 | 可提交 | 可取消 | 说明 |
|---|---|---|---|---|---|
| 草稿 | 0 | ✅ | ✅ | ✅ | 拟议值可反复修改；来源快照列永不变 |
| 已提交 | 1 | ❌ | ❌（不可重复提交） | ✅ | 冻结拟议快照并记录 `SubmittedAt`；只是登记冻结，**未批准、未套用** |
| 已取消 | 2 | ❌ | ❌ | ❌（不可重复取消） | 必须填写取消原因，记录 `CancelledAt` / `CancelledReason` |

- 控制器**没有** `DELETE` / `PATCH` 接口，也**没有**任何 `Approve` / `Apply` 动作（契约测试逐条断言）；
- 越权动作一律抛 `RuleConflict` 并给出照实说明（例如「已提交：拟议快照已冻结，不能再编辑」）。

## 3. 来源快照（登记时冻结）

登记时由服务端权威写入以下快照，之后**任何**编辑都不得改写这些列：

| 快照项 | 列 | 说明 |
|---|---|---|
| 来源标识 | `SalesOrderId` / `SalesOrderNo` | 单号快照；来源改名后历史申请按登记当时口径可读 |
| 来源状态 | `SourceStatus` | 登记当时 `DocumentStatus` 的整数值（只读文案对照） |
| 最后更新时间 | `SourceUpdatedAt` | `UpdatedAt ?? CreatedAt`，作为确定性快照标记的一部分 |
| 明细签名 | `SourceDetailSignature` | 「行数 + 明细合计 + 规范行串 SHA-256 前 32 位」：任何行数 / 商品 / 规格 / 单位 / 数量 / 单价变化都会改变签名 |
| 快照标记 | `SourceSnapshotMarker` | 确定性文本：`来源 <单号> · 状态 <文案> · 更新 <时间> · 明细 N 行 · 总额 <值>` |
| 主表快照 | `Source*` 26 项 | 日期 / 客户 / 业务员 / 币种 / 汇率 / 总额 / 定金比例与金额 / 条款 / 交期 / 运输方式 / 目的港 / 备注 / 客户 PO / 合同号 / 价格条款 / 收货人 / 通知人 / 唛头 / 来源报价单号 / 来源 PI 号 / 出口方式 / 佣金比例 / 业务性质 / 分批出货 / 验货要求 / 包装要求 |
| 明细行快照 | `SalesOrderChangeRequestDetails.Source*` | 逐行：商品 Id / 名称 / 规格 / 单位 / 数量 / 单价 / 金额 / 交期 / 备注 |

来源销售订单**只保存快照**：**刻意不建**到 `SalesOrders` / `SalesOrderDetails` 的外键，也不在来源订单上加列——
来源改名、停用或软删除都不影响历史申请可读，本模块也不参与来源订单的金额、库存、财务与出运计算。

来源校验：必须**存在且未删除**（否则 `NotFound`）、**未作废**（否则 `RuleConflict`）；未选择来源抛 `InvalidParameter`。

## 4. 拟议值与服务端金额重算

拟议值与客户端报文缺省语义（接口与界面同源）：

| 客户端取值 | 语义 |
|---|---|
| 可空字段（日期 / Id / 比例 / 币种 / 布尔）传 `null`（或数值 ≤ 0） | **沿用当前拟议值**（来源基线或上一次编辑） |
| 文本字段传 `null` | 沿用当前拟议值 |
| 文本字段传 `""` | **显式清空** |
| `Details` 传 `null` / 空集合 | 拟议**回到来源快照**（原样留痕），不会删除来源行 |
| `Details` 非空 | 必须**逐行覆盖全部来源行**（可标记移除），多出来的行视为新增行 |

金额口径（**不接受客户端合计**）：

- 明细金额 = 数量 × 单价；拟议总额 = Σ 明细金额；拟议定金金额 = 总额 × 定金比例 %；
- 校验：明细数量 > 0、单价 ≥ 0、定金比例 0~100、佣金比例 0~100、汇率 > 0；
- 全部复用 **`SalesOrderAmountRules`（销售订单唯一权威算法）**：ERP-047 把原先内联在
  `SalesOrderController` 的 `Calculate` / `Validate` 抽为共享实现，控制器改为委派调用，
  变更申请服务把拟议值装配成一张**未落库**的销售订单草稿后交给同一套算法 ——
  系统内不存在第二套销售订单金额算法（契约测试断言服务内无 `/ 100`、无 `.Sum(d =>`、无 `Quantity * ` 公式）；
- **先校验、后写入**：合并与校验都在**脱离跟踪的拟议副本**上完成，任何失败都不会给被跟踪实体留下脏状态，
  也不会写入半截数据（测试覆盖：非法请求后草稿拟议值保持原样）。

拟议报文契约：`SalesOrderChangeRequestSaveDto` / `...DetailSaveDto` **不含**任何 `Amount` / `Total` /
`Approved` / `Applied` 字段（契约测试用反射逐条断言）。

## 5. 明细对照（来源行 / 移除行 / 新增行）

明细行 = 「来源行快照 + 该行的拟议值」，一行一个持久化记录：

| 场景 | `HasSourceLine` | `ProposedRemoved` | 口径 |
|---|---|---|---|
| 未修改的来源行 | true | false | 拟议值 = 来源值；`ComparisonText` = 与来源行一致（未修改） |
| 修改的来源行 | true | false | 逐字段对照（商品 / 规格 / 单位 / 数量 / 单价 / 交期 / 备注），给出「拟议已修改」 |
| 移除的来源行 | true | true | 来源快照**完整保留**；拟议值一律回到来源值（不发明新值） |
| 拟议新增行 | false | false | 来源没有对应行；来源快照列留空 |

- 限制：行数上限 200；全部来源行都被标记移除（或拟议无剩余行）一律拒绝
  （「如需整体撤销，请取消本申请」）；行数少于来源行数一律拒绝；
- 新增行不得标记移除（它没有对应来源行）；
- 旧的「拟议新增行」在下次保存时按**软删除留痕**，来源行永远保留。

## 6. 来源变化检测（只提示、不刷新）

台账与详情都会显式报告「来源在登记快照之后是否已变化」：

- 对比项：**状态 / 最后更新时间 / 订单总额 / 明细签名**；
- `SourceChanged` = true 时，`SourceChangedText` 明确写出「不覆盖、不合并、不静默刷新拟议值，
  请人工核对后决定是否新建申请」，`SourceChangeDetailText` 逐项列出不一致的比对项；
- 来源已删除时 `SourceAvailable` = false，文案照实说明「已不存在或已删除：无法核对来源是否变化」，
  历史快照照常可读；
- 来源变化**不会**阻止保存草稿：申请始终是「登记当时口径 + 当前拟议值」，由人工决定后续动作。

## 7. 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/sales-order-change-requests` | 台账（分页，默认 50、单次上限 200）；过滤 `salesOrderId` / `status` / `keyword`（单号 / 来源单号 / 原因，≤100 字符） |
| GET | `/api/sales-order-change-requests/metadata` | 模块口径元数据（状态 / 币种白名单、上限、快照 / 金额 / 提交 / 审批边界文案） |
| GET | `/api/sales-order-change-requests/source-options` | 来源销售订单候选（只含未删除订单，≤200；已作废订单标注不可选择） |
| GET | `/api/sales-order-change-requests/by-source` | 指定来源订单的申请清单（≤200，单据行入口用） |
| GET | `/api/sales-order-change-requests/{id}` | 详情（来源快照 + 来源变化提示 + 主表 26 项对照 + 明细逐行对照 + 拟议原始值） |
| POST | `/api/sales-order-change-requests` | 登记草稿（来源校验 + 冻结快照 + 生成申请单号 + 重算金额） |
| PUT | `/api/sales-order-change-requests/{id}` | 编辑草稿（仅草稿；来源快照列不变；沿用权威算法重算） |
| POST | `/api/sales-order-change-requests/{id}/submit` | 提交（冻结拟议快照；不可重复提交） |
| POST | `/api/sales-order-change-requests/{id}/cancel` | 取消（原因必填；草稿与已提交都可取消） |

读取侧全部**批量装载**：台账页一次装载明细 + 一次装载来源订单（含明细），无逐行查询；
详情与写路径返回也走同一映射，保证界面显示与台账一致。

## 9. 数据库结构（幂等升级第 33 段）

- `db_owner.SalesOrderChangeRequests`（申请主表：来源快照 + 拟议值 + 提交 / 取消留痕）
  与 `db_owner.SalesOrderChangeRequestDetails`（明细：来源行快照 + 拟议值）；
- 只做 `IF OBJECT_ID(...) IS NULL` 幂等建表 + `IF NOT EXISTS` 建索引 / 外键，**不含任何 `UPDATE` /
  `INSERT` 回填语句**，也不对 `SalesOrders` / `SalesOrderDetails` 做任何 `ALTER`；
- 索引与 EF 模型同名同过滤条件：
  `UX_SalesOrderChangeRequests_RequestNo`（唯一，过滤 `IsDeleted = 0`）、
  `IX_SalesOrderChangeRequests_SourceOrder_Status`、`IX_SalesOrderChangeRequests_Status_CreatedAt`、
  `IX_SalesOrderChangeRequestDetails_Request_LineNo`；
- 唯一外键是「明细 → 申请」（`FK_SalesOrderChangeRequestDetails_Request`，级联）：申请本身仍只做软删除；
- 精度：数量 / 金额 / 比例 `DECIMAL(18,4)`、汇率 `DECIMAL(18,6)`，与 EF 模型声明一致；
- 单号字轨：`DocumentType.SalesOrderChangeRequest = 23`，默认前缀 `SOC`（不影响既有 `SO` 字轨）。
