# 外贸 ERP 系统 · 部署交付文档

> 项目名：NEWERP · 目标服务器：Windows Server 2022 + SQL Server 2022 + IIS

## 一、项目启动方式

### 开发环境启动
```powershell
# 1. 还原依赖
dotnet restore

# 2. 运行（默认 Development 环境，读取 appsettings.Development.json）
dotnet run --project src/ERP.Api/ERP.Api.csproj

# 浏览器访问 Swagger 接口文档
# http://localhost:5000/swagger
```

### 一键启动脚本（推荐）
根目录已提供两个 PowerShell 脚本，自动完成 SDK 校验、端口占用检查、依赖还原与启动：

```powershell
# 开发环境启动（Development，监听 http://localhost:5000）
powershell -ExecutionPolicy Bypass -File .\start-dev.ps1

# 发布产物本地验证（Production，监听 http://localhost:5001，运行 .\deploy\ERP.Api.dll）
powershell -ExecutionPolicy Bypass -File .\start-deploy.ps1
```

| 脚本 | 环境 | 端口 | 说明 |
|---|---|---|---|
| `start-dev.ps1` | Development | 5000 | 读取 `appsettings.Development.json`，源码热运行，日志写入 `src\ERP.Api\logs\` |
| `start-deploy.ps1` | Production | 5001 | 校验 `ERP_ConnectionStrings__Default`、`ERP_Jwt__Key` 环境变量后运行产物，日志写入 `deploy\logs\` |

> 停止服务：在运行窗口按 `Ctrl+C`。

### 生产环境构建发布
```powershell
# 发布（输出到 ./deploy/ 目录）
dotnet publish src/ERP.Api/ERP.Api.csproj -c Release -o ./deploy
```

## 三、数据库初始化

**方式一（推荐）：应用启动自动建表**
应用启动时执行 `EnsureCreated()`，自动创建全部 39 张表、索引，并写入种子数据（管理员、角色、菜单、系统参数、单据号规则）。首次启动需确保连接字符串有建库权限。

**方式二：EF Core 迁移（可生成 init.sql）**
```powershell
# 安装工具（仅首次）
dotnet tool install --global dotnet-ef

# 生成迁移并更新数据库
dotnet ef migrations add InitialCreate --project src/ERP.Infrastructure --startup-project src/ERP.Api
dotnet ef database update --project src/ERP.Infrastructure --startup-project src/ERP.Api

# 生成完整初始化脚本到 deploy/init.sql
dotnet ef migrations script --project src/ERP.Infrastructure --startup-project src/ERP.Api -o deploy/init.sql
```

**默认管理员账号：**
- 用户名：`admin`
- 密码：`Admin@123`（首次登录后请立即修改）

**第二阶段存储过程脚本（必读）：**
第二阶段（存储过程驱动版，单据主键 `Oid`、单据号 `BillNo`、状态 `Status` 1=保存/2=已审核/-1=已作废）需在首次初始化后执行数据库脚本：

1. `./deploy/init2.sql` — 平台表（`Plat_TableMaxID`/`Plat_CurrentBillNo`）与 8 种单据（销售订单/采购订单/询价单/采购入库/销售出库/收款单/付款单/定金申请单）的建表与 `sp_Biz_*` 存储过程。
2. `./deploy/init3.sql` — 补充 8 种单据（货款申请单/装柜结算单/散货结算单/客诉单/收货计划/订柜信息/预装柜单/装柜清单）的建表与 `sp_Biz_*` 存储过程，**必须在 init2.sql 之后执行**。
3. `./deploy/init4.sql` — **第四阶段增量升级脚本（新增）**：
   - 为全部 16 个 `sp_Biz_*` 增加「销审（`@Action='UnAudit'`）」分支（`CREATE OR ALTER`，不删表不删数据）；
   - 新建打印设计模板表 `db_owner.SysPrintTemplates` 与唯一索引；
   - 为 `db_owner.SysOperationLogs` 增加 `BillNo` 列（单据号追溯）。
   可由脚本 `tools/apply-init4.ps1` 自动执行（读取 `appsettings.Development.json` 连接串并按 `GO` 分批），也可在 SSMS 中直接打开执行。

> ⚠️ **重要**：`init2.sql` / `init3.sql` 内含 `DROP TABLE`，**仅适用于全新空库**；
> 已在运行的数据库升级请只执行 **`init4.sql`**（幂等、非破坏性）。
>
> 💡 应用启动时会自动执行 `SchemaUpgrader`：以 `IF NOT EXISTS` 方式补齐第四阶段新增的表与列，
> 因此**表结构无需人工执行 DDL**；但存储过程内的「销审」分支必须执行 `init4.sql` 后才生效
> （未执行时前端点「销审」会收到明确提示，不会静默失败）。

> 在 SQL Server Management Studio 中按顺序执行 init2.sql → init3.sql → init4.sql 即可；存储过程均已使用幂等保护，可重复执行。


> ⚠️ **脚本修复记录（2026-08-30）**：本次已修复两处脚本语法缺陷，请务必使用最新版本的 init2.sql / init3.sql：
> 1. `init2.sql`：原末尾残留一段无存储过程上下文的孤立代码块（PurchaseOrder 还原逻辑的重复片段），已删除，避免整批脚本执行时报语法错误。
> 2. `init3.sql`：`sp_Biz_FinancePaymentApply` 存储过程原缺少过程体收尾 `END`，已补齐；文件末尾孤立 `END` 已删除。

> ⚠️ **数据库 Schema 特别说明**：目标数据库 `WMERP_Data` 的现有表实际存储在 **`db_owner` schema**（而非默认 `dbo`）。代码已通过 `modelBuilder.HasDefaultSchema("db_owner")` 适配。若您在其他环境部署到全新的空库，EF Core 会按连接用户的默认 schema 自动建表（通常为 `dbo`），此时需将该配置改为 `dbo` 或保持一致。

## 四、Windows IIS 部署要点

1. **安装运行时**：服务器安装 [ASP.NET Core 8.0 Hosting Bundle](https://dotnet.microsoft.com/download/dotnet/8.0)，安装后执行 `iisreset`。
2. **创建站点**：IIS 新建站点，物理路径指向 `./deploy/` 目录。
3. **应用程序池配置**：
   - .NET CLR 版本：`无托管代码`
   - 托管管道模式：`集成`
   - 启动模式：`AlwaysRunning`（可选）
   - 空闲超时：建议设为 0（不回收，避免首次请求冷启动）
4. **权限要求**：
   - 应用程序池身份（默认 `IIS AppPool\<池名>`）需对 `./deploy/` 有**读取**权限，对 `./deploy/logs/` 有**写入**权限。
   - `logs/` 目录已随产物提供，若缺失请手动新建并授权，否则 stdout 日志与 Serilog 日志无法写入。
5. **web.config 说明**（源模板：`src/ERP.Api/web.config`，发布时由 SDK 自动补全 `processPath`/`arguments`）：

   | 配置项 | 值 | 作用 |
   |---|---|---|
   | `modules` | `AspNetCoreModuleV2` | ASP.NET Core 8 托管模块 |
   | `hostingModel` | `inprocess` | 进程内托管，性能最优 |
   | `stdoutLogEnabled` | `true` | 启用启动日志，排查站点起不来的问题；稳定后可改 `false` |
   | `stdoutLogFile` | `.\logs\stdout` | 输出到 `deploy\logs\stdout_*.log` |
   | `ASPNETCORE_ENVIRONMENT` | `Production` | 读取 `appsettings.Production.json`（敏感项留空，由 `ERP_` 环境变量注入） |
   | `maxAllowedContentLength` | `52428800` | 请求体上限 50MB，满足商品图片批量上传（IIS 默认仅约 28MB） |

6. **端口**：站点绑定 80/443，若占用可自定义端口。
7. **首次启动排查顺序**：
   1) 访问 `/swagger` 是否返回 200；
   2) 若报 500.30 / 500.31，查看 `deploy\logs\stdout_*.log`；
   3) 最常见原因是未注入 `ERP_ConnectionStrings__Default` 或 `ERP_Jwt__Key`（生产配置文件中这两项故意留空）。

### 8.2 缺陷修复（本轮自测发现）

| 缺陷 | 说明与修复 |
|---|---|
| 单据状态流转接口全部返回 405 | `[HttpPost("{billType}/{oid:long}/{action}")]` 中的 `action` 是 MVC 保留路由值，会导致找不到动作而返回 405（审核/作废/还原/删除此前实际不可用）。已改为 `{op}` 并加注释说明 |
| 打印模板接口提示「对象名 db_owner.SysPrintTemplates 无效」 | EF Core 默认表名取 **DbSet 属性名**（复数），手工 DDL 误用单数表名。已统一为 `SysPrintTemplates`，并在启动升级器中兼容重命名历史遗留的单数表 |
| 销审分支注入脚本生成错误 SQL | 首版以正则匹配审核分支结束位置，遇到「审核分支内部含 IF/ELSE」的单据（如采购订单）会截断代码块，导致 `sp_Biz_PurchaseOrder` 创建失败。已改为「逐行 + BEGIN/END 嵌套计数」算法 |
| 销审静默成功 | 未执行 `init4.sql` 时旧存储过程会忽略未知动作并返回成功。已在存储过程调用后回读 `Status` 做结果校验，未升级时返回明确提示 |

### 21.3 修复的 bug

#### Bug A：登录页 login-card 在窄屏被推出 viewport
- **根因**：旧 CSS 用 `grid-template-columns: 1fr minmax(420px, 480px)`，且 `@media (max-width: 1024px)` 切单列布局，640px viewport 下 login-card 被推到 viewport 外
- **修复**：改为 flex 布局，`.login-page { display: flex; min-height: 100vh }`，`.login-card { flex: 0 0 500px; align-self: center }`，banner 占剩余空间
- **响应式断点重新规划**：1500 / 1280 / 1024 / 768 / 480（桌面 → 平板 → 手机），520px 以下才上下堆叠

#### Bug B：login-btn width:33px
- **根因**：`<button>` 元素默认 inline-block，加 `.btn-block { width: 100% }` 在某些情况下未生效；`.input-wrap` 也缺 width: 100%
- **修复**：`.btn-block { display: block; width: 100% }` 强制 block + 100%；`.input-wrap { width: 100% }` 撑满父容器

#### Bug C：登录后 sidebar-nav 空、content 空
- **根因（双重 bug）**：
  1. `createNavGroup` 函数引用了未定义变量 `emoji`（`${emoji ? ... : ''}` 在 template literal 中正常返回 undefined 不抛错，但 group title 渲染异常）
  2. 用户浏览器的 disk cache 把旧版 `app.js` 缓存（HTTP 304 Not Modified），不重新加载新代码
- **修复**：
