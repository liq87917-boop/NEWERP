# 装柜费用分摊证据视图说明（ERP-060）

> 任务：`ERP-060` 把 ERP-042 **已持久化的分摊批次与分摊行**（一柜多客户费用分摊的留痕）以**只读**方式
> 呈现在**装柜清单详情**、**装柜结算单工作流**与一个有界分页的「分摊证据工作台」中：
> 有效批次条数、按「币种 → 客户」分组的分摊金额 / 比例、分摊方法与基数（含基数来源）、
> 未分摊参考、已作废 / 历史异常批次的历史视图，以及失效链接（参与方 / 客户 / 柜号）的逐行标注。
> 范围：`src/ERP.Application`、`src/ERP.Api/Controllers`、`src/ERP.Api/wwwroot`、`src/ERP.UnitTests`、
> `src/ERP.IntegrationTests`、`docs/**`、`.ai/**`。
> 本任务**不新增任何表、不新增任何列、不做任何结构变更**（`SchemaUpgrader.cs`、任何 `.sql`、
> `src/ERP.Domain/**`、`src/ERP.Infrastructure/**`、`deploy/**`、`release/**`、`checkpoints/**`、
> `SeedData*.cs` 均未改动）；**生产库执行、真实结算 / 记账、部署与发布仍由 Human Gate 控制**。
> 本次未启动 API、未连接 SQL Server、未执行任何 `.sql` / seed / 部署动作、未运行集成 / UI（Selenium）用例、
> 未做浏览器验收。

## 1. 背景与审计结论（为什么是「只读呈现」而不是「第二套分摊引擎」）

| 已有权威记录 | 作用 |
|---|---|
| `FinanceExpenseAllocationBatches`（ERP-042） | **分摊批次留痕**：批次号（`EAB-yyyyMMdd-序号`）、来源费用单、装柜清单 / 柜号快照、分摊方法、基数种类、币种 / 汇率、来源金额、分摊合计、行数、状态（有效 / 已作废）、作废时间与原因 |
| `FinanceExpenseAllocationLines`（ERP-042） | **逐行分摊留痕**：参与方 / 客户快照、方法、基数种类与来源、基数值、比例、分摊金额（原币 + 折人民币）、生成的费用单号 |
| `ContainerLoadingListParticipants`（ERP-041） | 一柜多客户的**参与方身份**（本视图用它校验分摊行的参与方 / 客户链接是否仍然成立） |
| `FinanceExpenses`（ERP-042 生成） | 分摊结果仍是既有费用单行（本视图按 `AllocationBatchNo` 归属留痕读取批次坐标，不重算金额） |

ERP-060 的审计结论是：**不新建表、不新增列、不复制任何分摊值、不重算金额**，只按**显式装柜清单 Id /
结算单 Id** 读取上述登记册并**派生呈现**：

- 金额一律取自批次与分摊行的**持久化列**（`SourceAmount` / `AllocatedTotal` / `LineCount` /
  `AllocatedAmount` / `Ratio`），界面与接口都不重算、不四舍五入改写权威值；
- 分组只有一级派生：`币种`（来自批次 `Currency`）与 `客户`（来自分摊行 `CustomerId`）；
- 未分摊参考只由「本柜柜级来源费用单」与「有效批次来源费用」两个显式持久化集合比对得出；
- 缺失证据显示「无（未登记任何有效分摊批次）」或「未知」，**绝不**显示为 0、已结算、应收或应付。

`docs/装柜费用分摊批次说明.md`（ERP-042）此前已把「按柜查看分摊结果」列为后续扩展，本次即为该扩展的落地。

## 2. 关联口径（显式持久化链接，绝不按文本匹配）

| 入口 | 关联键 | 缺失时行为 |
|---|---|---|
| 装柜清单详情 | `LoadingListId = 装柜清单 Id` 的 ERP-042 批次；柜级来源费用按 `RefType ∈ {整柜, 拼柜, 散货}` 且 `RefNo = 柜号` 匹配 | 未登记批次 → 「无（未登记任何有效分摊批次）」；未登记柜号 → 未分摊参考「未知」 |
| 装柜结算单详情 | 本单 **`LoadingListId`**（显式外键） | 未关联清单 → 证据「未知」，不按柜号 / 客户推断 |
| 工作台行 / 明细 | 显式**装柜清单 Id**（行由批次 `LoadingListId` 分组得出） | 清单已删除 → 标注不可用，留痕仍按原值可读 |

- 连接批次与客户一律走**持久化外键**（`LoadingListId` / `ParticipantId` / `CustomerId`），
  **不按柜号、客户名、批次号文本**挑选、合并或改派记录；
- 工作台的等值筛选（柜号 / 清单号 / 批次号 / 币种）为「去空白 + 统一大小写」的**显式等值**匹配；
  关键字只命中显式列（柜号 / 清单号 / 批次号 / 来源费用单号 / 客户编码 / 客户名称），不做相似度匹配；
- 清单与批次 / 分摊行 / 客户 / 参与方的装载全部**批量**（详情 6 次查询、工作台按页 4 次查询），
  与批次 / 行数无关，无逐行数据库访问。

## 3. 呈现口径（币种、客户、基数、未分摊）

| 维度 | 口径 |
|---|---|
| 币种 | 批次 `Currency`（沿用来源费用单币种）：**同一币种内可加总，不同币种不合并、不换算**，也不做任何跨币种合计；折人民币只展示批次留痕中**已持久化**的来源汇率结果（2 位小数），并按币种组分别展示 |
| 客户 | 分摊行 `CustomerId`（不按客户名文本合并）；客户已停用 / 已删除 → 标注不可用（历史仍可读） |
| 金额 | 原币、按币种精度取整（`JPY` 等 0 位小数币种不补小数）；客户金额 / 比例来自分摊行，币种合计取自批次持久化列 |
| 基数 | `AllocationMethod`（按体积 / 按重量 / 按箱数 / 按金额 / 整柜）+ `BasisKind` + `BasisSource`（持久化装柜证据 / 用户确认请求值）+ `BasisValue`，逐行显示「来源：…」证据文案 |
| 有效 / 已作废 | `Status = 1` 计入**有效合计**；`Status = 0`（已作废）与**历史异常状态**只进入历史视图，不参与任何合计 |
| 未分摊参考 | 只看本柜**柜级来源费用单**中「不属于任何有效批次」的那些（按币种单列条数 / 金额 / 费用单号）；其中所属批次已作废的会单独计数并提示「需重新分摊」 |
| 历史分摊行 | 费用单自身带分摊基数 / 比例或分摊金额但**无批次留痕**（ERP-042 之前的历史口径）→ 只作只读辨识计数，既不进入未分摊参考，也不做任何回填 |
| 失效链接 | 参与方不存在 / 不属于本柜 / 参与方客户与分摊行客户不一致 / 客户不可用 / 批次柜号与清单柜号不一致 / 清单已删除 → 逐行标注状态与原因，**不改派、不修复、不按文本重新匹配** |

**绝不发生**以下事情（单元测试逐条锁定）：

1. 缺失分摊证据不会显示为 0、已结清、已结算、应收或应付；
2. 不同币种之间永不合并或换算（即使金额数字相同）；
3. 已作废 / 历史异常批次不会被计入有效合计，也不会被删除或改写（只做历史呈现）；
4. 失效链接不会被静默修复、重指派或按客户名 / 柜号文本重新匹配；
5. 未分摊参考不会被解释为「该柜费用为零」或任何收付款状态；
6. 装柜结算单的 `TotalAmount` / `FreightCost` / `OtherCost` / `CustomerId` 只作**原值回显**，
   分摊证据既不参与结算金额计算，也不会写入结算单的任何字段。

## 4. 装柜结算单的金额对照（算术证据）

结算单未持久化币种列，因此对照口径严格受限：

| 情形 | 结果 |
|---|---|
| 无有效分摊证据（含只有已作废批次） | `comparisonComparable = false`，文案说明「无法对照」，并强调「无」≠ 零费用 / 已结清 |
| 存在**多个**币种组 | `comparisonComparable = false`，文案说明「不合并、不换算，因此不做任何合计对照」 |
| 恰好**一个**币种组且有有效证据 | `comparisonComparable = true`，给出 `结算单总金额 − 有效分摊合计 = 差额`（该币种精度取整） |

任何情形下该差额都标注为**算术证据**：结算单未记录币种列、该差额不构成结算差异 / 应收应付 / 对账 /
已结算结论，也与是否已收付款无关。

## 5. API（全部只读）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/container/expense-allocation-evidence` | 分摊证据工作台（分页有界；显式字段筛选） |
| `GET` | `/api/container/expense-allocation-evidence/loading-lists/{loadingListId}` | 按显式装柜清单读取分摊证据 |
| `GET` | `/api/container/expense-allocation-evidence/settlements/{settlementId}` | 按显式装柜结算单读取分摊证据 |
| `GET` | `/api/container/loading-lists/{id}/expense-allocation-evidence` | 装柜清单详情入口（只读） |
| `GET` | `/api/finance/container-settlements/{id}/expense-allocation-evidence` | 装柜结算单工作流入口（只读） |

工作台查询参数（全部为可选筛选，未知取值一律 400）：

| 参数 | 口径 |
|---|---|
| `page` / `pageSize` | 分页（默认 20，单次上限 200，越界自动收敛） |
| `containerNo` / `loadingListNo` / `batchNo` / `currency` | **显式等值**（去空白 + 统一大小写；长度上限 100） |
| `status` | 批次状态（1 有效 / 0 已作废；其他取值一律 400；留空 = 全部，含已作废历史） |
| `customerId` | 显式正整数 Id（按分摊行的客户链接匹配，不按客户名文本合并） |
| `includeHistory` | 是否包含已作废 / 历史异常批次（默认 `true`） |
| `keyword` | 只命中显式列（柜号 / 清单号 / 批次号 / 来源费用单号 / 客户编码 / 客户名称），长度上限 100 |

**读取性能口径**：单个装柜清单的证据装载固定为 6 次批量查询（装柜清单 / 批次 / 分摊行 / 客户 /
参与方 / 柜级来源费用），工作台按页再固定 4 次（本页装柜清单 / 本页分摊行 / 客户 / 参与方）；
一切扫描有界（批次 ≤ 200、分摊明细 ≤ 2000、来源费用单 ≤ 50、历史视图 ≤ 200），
截断时在界面与证据文案中**显式说明**（合计仍取自批次持久化列，绝不用截断后的行重算权威值）。

## 7. 边界（本任务明确不做的事）

1. **只读**：服务层与控制器没有任何 `Add` / `Update` / `Remove` / `SaveChanges`，全库查询均为
   `AsNoTracking`；不改写装柜清单与明细、参与方、分摊批次与分摊行、费用单、结算单、客户主数据；
2. **不新建任何表 / 列**：无结构变更、无 `SchemaUpgrader` 改动、无任何回填（老柜子没有批次时照实显示「无」）；
3. **不记账 / 不结算 / 不付款**：不生成凭证、收款单、付款单、结算单，也不改变任何单据状态或工作流；
4. **不推断**：不重算比例与金额、不推断缺失基数、不把「无 / 未知」读成零费用或已结清、
   不给客户或柜组件任何应收应付或对账结论；
5. **不按文本匹配**：不按柜号 / 客户名 / 批次号文本合并或改派记录，也不跨币种、跨客户合并；
6. **不改写下游**：销售订单、采购订单、库存与库存成本、库存流水、单证中心、发票与税务记录均不受影响。
